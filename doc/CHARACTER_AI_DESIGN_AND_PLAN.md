## 1. 背景与设计目标

当前 `g2-local` 基线已有 V5 C#/.NET 麻将规则、三绝技权威裁决、本地单机宿主（`Mahjong.LocalHost`）、批跑工具（`CheatAiBatchRunner`）及 `octopus` 的袖里藏花特性。`LocalTableDriver` 现有普通动作与千术分别取候选和提交，批跑器逐局启动 LocalHost 并统一使用随机千术策略。Unity Local Lite 入口当前只传入选中的玩家角色，AI 千术默认关闭。

本方案目标是在**不破坏 V5 核心不变量**的前提下，分阶段构建**“低延迟、小包体、可增量扩展千术、具备鲜明角色个性”**的 AI 系统：

1. 先以启发式策略贯通座位级角色、千术候选和权威提交，再训练无千术骨架（L1）、千术适配器（L2）和角色条件层（L3）。
2. 每个冻结的决策窗口最多执行一次模型前向。桌面端完整 AI 决策路径的目标为 P99 `< 5ms`，短窗口或推理故障走同窗口的启发式或安全默认动作。
3. `Mahjong.Ai` 保持纯托管 `.NET Standard 2.1` / C# 9。首批产品入口为 Unity Local Lite（Windows / Android），`.NET 8` 批跑器复用同一策略和规则语义。独立远端宿主可复用接口，接入和验收另行安排。

## 2. 必须遵守的架构红线

- **物理守恒与信息隔离**要求一副 136 个实体 ID 全程守恒。策略只消费本席冻结的普通观测和经授权的千术候选。权威端负责资格、牌面可见性、费用、窗口、状态转换与结算。
- **确定性与哈希边界**限定模型打分、`HeuristicScore` 和 PPO 采样只影响动作选择。权威状态、`CommandIntent.AuthorityHash` 和账本沿用规则与实际提交的动作。恢复按已记录的请求、回执和状态对账。
- **截止时间以权威时钟为准**。模型调度在权威串行队列外进行，提交回队列后重新校验身份及窗口。`now >= deadline` 时由既有权威超时流程处理，迟到的模型结果失去提交资格。
- **训练工具独立部署**。Python / Colab TPU 脚本放在 `tools/ai-training/`，常规 `.NET` 测试和 Unity 启动无需 Python 或训练环境。

## 3. 三层模型架构设计（训练分层、推理合一）

采用共享骨干和独立动作头。`1M ~ 2.5M` 参数为原型规模估计，权重文件和产品包体以实际导出和构建测量为准。一次前向只服务一个窗口。付费激活、根据新 offer 选牌、出牌均从各自的新权威观测开始。

```text
[输入 1] BoardFeatures [B, C, 34]
   │
   ▼
Suit-Isolated 1D-Conv Stem (kernel=3，万/筒/索各自卷积不跨花色，字牌 1x1 投影)
   │
   ▼
6× 1D-ResNet Blocks (channels=96) ◄── [L3: FiLM(γ, β)] ◄── CharacterStyle [B, S]
   │
   ▼
2× Lightweight Self-Attention (34 种牌全局交互) ──► h_board [B, 192]
   │
   ▼
h_state = h_board + Zero-Init Residual Adapter(h_board, CheatContext) [L2]
   │
   │
   ├──► [Head 1: 普通动作头] + LegalActionFeatures ──► 动作 logits ──► Mask(LegalActions)
   │
   ├──► [Head 2: 千术 Pointer 头] [L2] ──► Cross-Attention(h_state, CheatOptions[B, M, F_opt])
   │                                      ──► Mask(cheat_mask) ──► 激活、跳过或解决 offer
   │
   └──► [Head 3: 价值头 (仅训练)] ──► 预测当前座位的回报
```

### 3.1 第一层（L1）：麻将骨架层（Base Backbone）
- 编码合法牌桌观测和普通动作候选，用于向听推进、听牌/立直判断、读牌河防守与打点评估。
- 关闭 AI 千术激活，使用全 AI 牌局并固定开局配置。先接 `BasicAiStrategy` 做行为克隆（BC），再通过已有 `TargetAwareAiContext` 接入 `SuitGoalAi`、`HonorTripletGoalAi` 或 `KokushiGoalAi`。中性骨架以 Basic 为教师，对手可轮换。目标策略的标签按教师保留，供后续角色条件训练使用。同一观测可有多个合理选择，每条记录使用对应教师实际选择的候选。
- 首批 L1 训练以单局为 episode，用结算确认的本席净分差作为终端回报，固定缩放。整场顺位另走 `LocalMatchCoordinator` 评估。如果后续使用整场顺位奖励，应随训练数据升级 episode 与终止定义。BC 先建立可部署基线，PPO 在采样链路通过验收后进行。

### 3.2 第二层（L2）：千术能力层（Cheat Adapter + Pointer Head）
- 在 `h_board` 加上输出层初始化为零的千术残差。冻结 L1 骨干和普通头开始训练。用相同普通输入、mask、数值精度和中性风格核对挂载前后的普通动作 logits 和选择。开放千术候选后，整体策略的行为由新增窗口与动作共同决定。
- Pointer 头只为权威端已冻结的合法候选评分。`octopus` 第三候选由权威规则和投影提供。候选协议和能力版本的兼容方式见 §4.2 与 §4.3。

### 3.3 第三层（L3）：角色风格层（Character FiLM / LoRA）
- 用同一骨干表达进攻、偏好副露或染手、偏好防守以及千术花费时机。例如 `octopus` 风格可在远离听牌时降低花费、在一向听或听牌时提高袖里藏花激活意愿。第三候选资格仍由规则角色裁决。
- 首选 FiLM 的五维条件向量 `[进攻倾向, 副露倾向, 染手倾向, 防守度, 千术激进度]`，中性条件在 L3 启用前等价于恒等映射。LoRA 保留为 FiLM 经对照未达风格目标时的备选，届时另测包体、装载时间与切换成本。

## 4. 工程模块详细设计

### 4.1 座位级角色与策略绑定（Domain + LocalHost）

- **规则角色由权威持有。** `CheatState` 将单个 `PlayerCharacterId` 扩为座位顺序固定的四席角色 ID，保留特性规则版本。`CheatSubmission` 在本人普通摸牌、岭上及他家回合等适用路径按动作所属座位查角色，逐个核对原有触发条件。角色选择在开局时确定，真人断线、托管或收回控制时沿用本席规则角色。
- **AI profile 由宿主按席装配。** `LocalAiOptions` 和 `LocalTableDriver` 支持每席配置策略 ID、风格、`AiCheatPolicy` 和可选模型版本。`LocalMatchCoordinator` 将同一规则角色及 profile 传给新局。Unity `LocalTableChannelFactory` 为电脑座位传入显式 profile 并按配置启用千术，已有默认入口沿用当前行为。真人托管使用单独的托管策略，默认禁止发起付费千术，已付费的 offer 仍可通过安全选项结清。策略状态和每局已花费按席隔离，花费从权威账本取得。
- **按原版本验证并迁移存档。** `TableCheckpointCodecs` 按旧 schema 读取并校验原指纹，再将旧角色映射到 0 席，其余席填 `player`。无角色字段的旧档四席均填 `player`。新 schema 记录四席角色及特性版本，并验证按席次计算的指纹。覆盖旧 `player` 和 `octopus`、含待决第三候选的冷恢复、已扣费但回执未确认、重复提交、跨局传递及异常版本拒绝。恢复原 offer、实体牌、扣费和回执关系，继续按恢复后的权威时钟处理窗口。求值所用 profile 或模型不可用时，按宿主配置进入启发式兜底。
- **评分式启发式先于模型。** `ScoredCheatBasicAiStrategy` 只使用 §4.2 的公开及本席授权事实。按候选类型用 `AiCheatHeuristics.TileValue`、已知牌的向听差、费用、保留点数和显式可见风险进行评分。激活前按期望收益评分，看到明确候选后再比较实际牌理。保留 `RandomCheatBasicAiStrategy` 作为对照。拒绝或超预算时按窗口采用 §4.4 的兜底。

### 4.2 可见观测、候选与动作提交合同

`AiCheatOpportunity` 当前带有本席余额和部分窗口身份，但每个候选只暴露 ID、费用和少量标志。`TableActor` 当前的 AI 即时袖里藏花只有前两项，偷梁换柱使用第一张可交换手牌，且 AI 未接入他家回合袖里藏花预约。实现时优先扩展现有本席投影与候选类型，复用 `AiSeatSnapshot` / `AiCheatView` 中适用的结构。普通和千术可以保留独立提交入口，并共享以下约束。

- **同一次捕获生成观测和可提交候选。** 权威端按座位提供当前窗口、deadline、本席余额及已花费、阶段、合法候选和必要的可见事实。普通动作保留每个原始 `LegalActionOption`，包括牌实体、实际消耗的手牌组合及候选 ID。千术保留当前合法选项、费用、目标、授权预览和安全默认。权威请求及 `TableAiCheatPlan` 留在宿主，策略只返回当前候选索引或 ID。
- **普通动作按候选打分。** 候选特征包含动作类型、目标牌、消耗组合和可见属性。应能区分红五与普通五、同牌种摸切与手切、同一弃牌的不同吃牌组合及各类杠。解码使用捕获的原始候选，禁止从牌种或动作名重建命令。
- **千术按阶段评分。** 首批接通落汗、本回合袖里藏花及偷梁换柱的权威候选。付费激活时提供费用和合法的公开或本席事实，预览按实际授权时点出现。已付费的袖里藏花按投影提供可见候选，规则允许时包含第三张。偷梁换柱只提供权威许可的交换组合及可见牌面，暗槽使用未知标记。开局码牌和他家回合袖里藏花的 AI 激活延期接入，已有真人规则、结清与回放继续走原权威路径。
- **“不使用”只用于可选激活。** 千术索引 0 为“不使用”，选中后推进正常流程。已付费 offer 将其 mask 掉，并保留权威提供的 `IsSafeDefault`。模型缺失、候选无效或能力版本不兼容时，激活窗口跳过，已付费 offer 提交安全默认。预算、能力开关及托管限制筛选新付费动作，已付费选择走本窗口的合法集合。
- **提交绑定于捕获窗口。** 保存 `roundId`、seat、`decisionId` 或 offer/window ID、状态版本、控制代次、恢复代次及 deadline。回到 actor 串行队列后按捕获的身份重新校验，通过才复用原权威提交入口。逐项覆盖目前 `LocalTableDriver` 的普通命令分支和千术分支。旧窗口、换局、恢复或收回控制后丢弃结果。对未决提交先用原请求对账，按权威回执决定后续动作。

### 4.3 特征编码器（`AiFeatureEncoder` in `Mahjong.Ai`）

- **`BoardFeatures [C, 34]`** 包含本席闭手计数（4 平面）、当前摸牌、四席可见副露计数、按席的牌河计数及立直状态、宝牌指示牌、各牌种未见枚数，再加场风、自风、局数、本场、立直棒、剩余牌山计数及点差。按相对于本席的座位顺序编码。用可见特征保留红牌、牌河顺序和被鸣牌事实。每个牌种的未见枚数为 4 减去已知实体牌的去重计数。
- **`LegalActionFeatures`、`CheatContext`、`CharacterStyle` 与 `CheatOptionFeatures`** 从 §4.2 的捕获生成。千术上下文包含点数、已花费、储备线余量、阶段和 offer 标志。千术候选编码能力、费用、可见目标、默认标志、收益估计与风险。候选的相对槽位由捕获顺序决定。千术张量首版为 65 槽，最多 64 个真实候选加第 0 槽。权威侧受限枚举按固定顺序保留安全默认，padding 全部 mask。普通动作张量容量须用实际合法枚举边界验证，超过容量时走整窗启发式。未知能力或布局版本回退到启发式或安全默认。
- **冻结特征版本。** 训练导出、模型清单和运行时共享张量名、形状、字段顺序、归一化、mask 与候选序。固定样本校验 C# 编码、训练读入和推理解码一致。绝对 deadline、请求 ID、控制代次和种子只用于调度、对账或离线分组。牌山顺序、对手暗牌和未授权候选不进入编码器。用改变隐藏状态但维持同席可见事实的配对场景验相同特征。
- **编码阶段稳态零托管分配。** 用 `Span<float>` 写预分配或池化缓冲区。投影、后端绑定、排队和冷启动的分配与耗时单独记录。每次在途推理独占其输入与输出，等实际调用完成再归还。

### 4.4 推理后端、软预算与兜底（`Mahjong.Ai` + 宿主）

- **后端与模型版本。** 在 `Mahjong.Ai` 暴露 `IModelInferenceSession` 纯托管接口，后端由组合根注入。`.NET 8` 批跑先验证 ONNX Runtime CPU，`IntraOpNumThreads = 1` 为起始配置。Unity 先验证 Sentis CPU 的 FP32 图，在加载阶段预热。固定后端版本、ONNX opset、算子支持和模型清单。量化由端侧验证决定。Sentis 2.4.1 官方表列出 `QuantizeLinear`、`DequantizeLinear`、`QLinearConv` 等不受支持的算子。可验证 Sentis 自身量化，或单独验证 ONNX Runtime 原生插件、Android ABI 与包体。[Sentis 算子表](https://docs.unity3d.com/Packages/com.unity.ai.inference@2.4/manual/supported-operators.html)
- **宿主统一管理预算。** 普通和千术推理都在权威队列外执行。以宿主的单调时钟计算剩余时间，软预算的起始值为 `min(30ms, remainingMs * 0.6, remainingMs - submitReserveMs)`。剩余不足 15ms、无法在预算内取得工作槽、处于熔断或软预算非正时，直接用兜底。`submitReserveMs` 按实际编码、排队和提交测试校准。后端使用有界并发。每席同一窗口最多启动一次模型求值，模型结果和兜底只允许一路进入提交。
- **软超时停止等待，权威端决定后续。** 超时后标记该任务失效并尽力取消后端，调度器立即在原窗口仍有效时走兜底。ONNX Runtime 用本次调用的 `RunOptions.Terminate` 连接取消。后端未退出前保留工作槽和缓冲区，拒绝将迟到结果应用到牌局。房间退出、换局、控制权收回或恢复时废止相关工作，退出等待有界并由后端负责释放仍占用的资源。[ONNX Runtime RunOptions](https://onnxruntime.ai/docs/api/csharp/api/Microsoft.ML.OnnxRuntime.RunOptions.html)
- **按窗口选择兜底。** 普通动作走 `BasicAiStrategy` 或已有安全默认，付费激活窗口跳过，已付费 offer 在仍可提交时选择权威安全项。权威 deadline 已到时交由既有超时流程。每席每局连续 3 次软超时后切到启发式，新局复位。故障注入要覆盖不响应取消、迟到完成、队列拥塞和兜底提交，记录软超时、权威超时、旧结果丢弃及采纳的兜底回执。

### 4.5 Colab TPU 训练闭环（`CheatAiBatchRunner` + PyTorch/XLA）

- **Actor。** 扩展 `.NET 8` 批跑器支持可配置座位教师、关闭 AI 付费激活和版本化张量分片导出（`.npz` 或二进制）。首版复用 LocalHost 小样本跑通。按 `episodeId` 和座位记录有序的冻结特征、候选 mask、选中索引、教师或策略版本、回执状态与结算结果。一次决策发生重放时按原请求去重。拒绝、回退与超时保留单独标记供诊断，BC 以符合条件的实际应用动作作标签。
- **PPO。** 模型自博弈时每条轨迹补齐行为策略版本、同一 mask 下采样动作的旧 log-prob、价值估计、奖励、终止标记及后续本席观测或 bootstrap 值。按真实权威执行结果形成轨迹。发生拒绝、超时或兜底时标记该步，从该步截断本席训练轨迹，避免将模型动作的 log-prob 配到兜底动作。首次训练先核对短轨迹与奖励回传，再开启多个 actor。每批轨迹与采样模型版本绑定。
- **Learner。** 按 episode 和基础种子分组切分训练、验证、测试，配对座位轮换归同组。`PyTorch/XLA` 使用固定形状和 mask，目标 batch `1024 ~ 4096`，从通过短预检的配置扩容。导出记录规则、观测、模型、教师版本以及分片哈希和切分清单。ckpt 与数据分片用配置好的产物目录保存。训练工具的诊断日志记录元数据，授权座位的特征只写到离线数据集。
- **奖励。** L1 采用 §3.1 的终端得分。L2/L3 的风格奖励可包含目标役种或副露、减少放铳、千术花费和收益。训练前定义公式、权重和归一化，并报告不含塑形项的规则收益，防止频繁鸣牌或频繁出千虚增风格指标。

## 5. 分阶段开发计划与验收门禁

### Milestone 1 · 权威候选、四席角色与评分式基线（纯 .NET）

预计 **14–22 人日**，含实现、回归和常规返修。首批通过 LocalHost 验证落汗、本回合袖里藏花和偷梁换柱。M2 承接张量编码、异步推理调度及端侧模型预检，M4 完成 Unity 特色 AI 产品入口。

### Milestone 2 · 数据与端侧可行性预检

1. 实现 §4.3 编码和 §4.4 宿主调度，接入推理故障桩。覆盖错误或非有限输出、不响应取消、超时后仍返回、队列拥塞、换局、收回控制权和 offer 到期。还来得及提交的窗口须采纳预期兜底，已到期窗口须走权威默认。逐条核对回执、权威后态和迟到结果计数。
2. 实现 `--export-dataset`，先生成一批 BC 样本并逐条核对记录和权威回执，再用一次短 PPO rollout 验证采样、掩码、奖励、终止及回退截断。固定样本通过 C# 编码、Python 读入与推理解码的一致性校验。
3. 用随机权重的代表性小图覆盖计划使用的卷积、注意力和普通／千术候选头。在 `.NET`、Windows Player、目标 Android IL2CPP 运行同一组测试向量，验证导入、预热、固定输出与端到端耗时。记录候选后端版本、平台、ABI 和包体增量。
4. **通过条件。** 数据往返与端侧预检均通过后进入大规模训练。失败依据短预检证据调整特征、图或后端，沿用启发式交付路径。

### Milestone 3 · L1 无千术骨架训练与部署

1. 复用 M2 数据合同，从 Basic 教师生成百万级合法训练样本，完成 L1 BC。经短轨迹验证后进行无千术 PPO 微调，并保留 BC checkpoint 作为对照。
2. 导出已通过 M2 的推理图，模型清单记录版本、输入输出、后端配置和文件哈希。量化候选需要重新验证固定样本结果、对战效果、延迟及包体。实际 Unity 入口核对模型缺失或版本不兼容时按配置降级。
3. **通过条件。** 无千术 1000 局配对对照达到 §5.1 对 Basic 的效果门禁。Windows Player 的完整 AI 决策 P99 `< 5ms`，L1 模型文件 `< 6 MB`，同时报告完整包增量。Android 按 M2 冻结的目标机型与决策／帧耗预算单独判定。

### Milestone 4 · L2 千术、L3 角色风格与产品入口

1. 先验证 L2 零初始化下普通动作输出与 L1 对齐，再开启首批千术做配对训练和评估。L2 单独通过点数预算、已付费 offer 与普通动作回归后，再训练 L3 FiLM。先用 `octopus` 与中性风格配对验证角色差异。
2. 在 Unity `LocalTableChannelFactory` 装配特色 AI profile。用 Windows Player 和目标 Android 包验证玩家能进入特色 AI 对局，并经真实牌局观察到合法千术激活和 offer 选择。执行换局、暂停恢复、模型降级及完整牌局回归。
3. **通过条件。** §5.1 的风格指标和牌力下限达标，权威守恒、账本一致性、超时以及 Windows／Android 性能预算通过。产品包及实机证据按平台记录。每项结果用于判定本计划的交付范围，G2 验收使用既有独立矩阵。

### 5.1 对照实验与证据口径

- **配对与分母。** 冻结测试种子、同一配置下的对手、席位轮换和实际局数。每组按同一基础种子和座位安排运行对照，隔离洗牌与策略随机流。同一配对分组作为统计单位。独立单局报告净分差和胜率，整场用 `LocalMatchCoordinator` 报告平均顺位。保留每种动作的实际合法机会、动作次数、失败、超时和未运行数。
- **效果门禁。** M1 的主要指标是评分式策略对随机千术策略的配对净分差，M3 的主要指标是 L1 对 Basic 的配对净分差。预先登记最低有意义效果量和配对 95% 置信区间算法，通过条件为点估计达到预设效果量且区间下界大于 0。M4 每个角色预先列出主风格指标及允许的最大净分／放铳率退化。先用相同规则角色对比不同风格，再固定风格对比有无规则特性。未达样本量或区间结论不确定时保留原基线，记录未达标项。
- **行为及 ROI。** 立直、副露及千术激活率同时报告动作数和合法机会数，第三候选出现率另以合格激活数为分母。用同种子、同座位、同普通策略的无千术对照计算净分增益，除以测试组实际花费的千术点数得到对战 ROI。花费为 0 时标记不适用。按能力记录发起、扣费、选择、默认、拒绝及合法机会，终局总分和出千点账本分别核对。
- **不变量与时效。** 千局批跑逐局检查终态 136 个实体 ID、得分与立直棒总量及账本。固定场景还检查激活、选择、拒绝、超时、恢复等关键转换的前后实体和账本，核对请求、回执及权威后态。为模型、启发式兜底和权威超时分别记录结果和耗时，端到端耗时从冻结观测至选定候选，并单独记录权威提交耗时及剩余余量。
- **平台与长验证。** 冻结 Windows／Android 的 Unity 版本、后端和 Player 配置，写明 Android 机型、ABI、帧耗、内存、冷启动及包体预算。对同一构建报告冷启动、稳态 P50/P95/P99、GC 分配、帧耗、回退率和安装包增量。共享 Unity、设备资源及长批跑按[长验证模板](LONG_VALIDATION_TASK_TEMPLATE.md)和[复核协议](v5-重构/V5-REVIEW-REWORK-PROTOCOL.md)执行。先完成短预检和固定正负例，使用独占输出、600 秒共享资源上限、30 秒心跳、有界取消并保留首败及产物哈希。
