# 四部分测试设计

日期：2026-11-09。设计最初基于 `g2_base` 的 `e074806a39a674b898120c828038efcd1b5c58d7`；本次迁入 `main` 的起始 commit 为 `93ce7cc7b4a2599f8a83ac41e8d8fde110a5e7d5`，工作树为 `D:/majiang-wt/main`。本文规定目标职责、场景与通过标准；新增执行器、测试标签及未覆盖场景均为待实现，不代表本轮已经运行或通过。当前测试规模、Kotlin清理后的来源门禁和实际覆盖口径以[测试说明](TESTING.md)为准。

## 1. 四部分的职责

| 部分 | 核心问题 | 运行环境 | 主要输出 |
|---|---|---|---|
| T1 代码单元测试 | 给定输入，代码规则、状态与算法是否正确？ | .NET / 必要 Unity EditMode；显式时钟、内存依赖 | 逐例 XML、输入/预期/实际、失败诊断 |
| T2 启动服务后的客户端脚本测试 | 真实服务能否通过客户端接口正确处理各种操作及故障？ | 独立 .NET 服务进程 + 脚本化真实 Client；需要时使用隔离 PostgreSQL | 服务身份、客户端动作、回执/事件/快照及持久化核对 |
| T3 Unity Test Framework 动画测试 | 已确认的游戏变化是否被正确、完整、可中断地表现？ | UTF PlayMode 为主，EditMode 检查静态资源 | 动画对象/阶段/时间、关键帧、队列与清理结果 |
| T4 最终端到端测试 | 同一最终交付包是否可从真实输入完成完整游戏流程？ | 分为 T4-WIN 和 T4-ANDROID 两个独立分块；按产品模式连接真实服务或本地宿主 | 各平台独立的包身份、输入到回执关联、画面/生命周期与整场结果 |

现有 .NET、EditMode、PlayMode 是执行载体，不是四部分的等价分类。真实 socket/文件/数据库测试即使写成 xUnit，也属于 T2 的集成范围；现有 PlayMode 的协议/规则断言可以作为辅助，不自动成为动画完成证明。

PowerShell 的参数、路径、解析器和判定函数回归归入 T1 工具测试；真实进程超时、退出码传递、故障注入及清理验证归入 T2 工具集成。工具结果单独汇总，不计为游戏功能通过。

## 3. T2：真实服务 + 客户端脚本

### 3.1 主执行路径

```text
进程监督器
  → 启动当前候选构建的独立 Lobby/TableService 进程
  → 等待有界健康检查及实际连接就绪
  → C# 客户端脚本（Mahjong.Client / TableSession）
  → WebSocketTableChannel → HTTPS/WSS 服务入口
  → 权威规则 / 事务提交
  → 回执 + 可见事件 + 全量/后续快照
  → 独立结果断言及必要的服务端只读审计
```

“客户端脚本”优先是引用现有 Client 的 C# 控制台驱动，由 PowerShell 启动服务和驱动；不另写一套普通业务协议客户端。四个玩家和观战者使用独立身份、会话、scope、outbox 和接收循环，不共享可变私有缓存。

普通动作从客户端当前合法候选构造；非法/过期业务请求有意构造错误参数并走同一生产接口。畸形帧、超长包、错误消息类型等协议负例可复用原始 TableTestClient，但结果单列，不冒称已验证真实 TableSession 行为。

本地存档与 LocalHost 适配器集成也归入 T2：在独立本地客户端 worker 内经生产 ITableChannel 操作、在进程间验证冷恢复。它不虚构本地 socket，不替代上面的独立远端服务链路。

### 3.3 固定场景与断言

固定场景应包括：开局、碰/吃窗口、立直/双立直、暗杠/大明杠/加杠/抢杠、庄家/闲家和牌、荒牌流局、连庄、三绝技与控制权/恢复边界。初态通过合法完整牌山、真实前置动作或已认证持久快照形成，保留来源/哈希。

现有 LocalPlayerActionScenario 只直接提供五种动作初态，不等于全部服务端场景已经具备。独立服务如何绑定固定局面需通过仅测试宿主装配的受控机制实现；不得新增对外生产接口供普通客户端改手牌/比分，也不得事后注入成功回执或终态。

每一步核对：
- 请求身份、round/decision/control epoch、scope、载荷摘要和评估版本。
- Applied/Recorded/Rejected 按真实契约解释；一个请求恰好产生预期效果，不能把“等待响应完成”误当最终状态已推进。
- 回执、目标事件和同一提交后态一致；event序号、回执高水位、版本和流游标分别核验，不假定相等。
- 拒绝路径的状态、事件、费用、outbox、实体效果为零；允许的协议拒绝/审计记录另行分类。
- 完整136实体和隐藏区域由受控服务端只读审计器核对；不得把完整牌山交给普通客户端或脚本决策策略。

使用带 deadline 的条件等待，不靠固定 sleep 决定动作成功。故障注入后先证明故障发生在目标提交点，再观察恢复；仅收集到JSON或进程exit 0不能判PASS。

## 4. T3：UTF 动画与表现测试

### 4.1 输入、驱动与观察

```text
有身份/版本/可见性绑定的事件及快照
  → 现有投影器 / ConfirmedAnimationQueue / Presenter
  → 实际场景、牌张对象、UI与动画组件
  → 检查初始帧、运动/过渡阶段、结束帧及清理
```

输入优先复用 T2 保存的脱敏可见事件记录；小型合成记录必须标记为夹具，并覆盖格式、身份和授权前置。不要让每个动画测试都从菜单建房或完整跑一局；仅保留少量真实服务→Unity表现的连接样本。

队列排序/去重等纯逻辑在 T1 快速验证；T3 必须实际加载所测场景/Prefab，通过帧推进观察对象。验证位置/缩放/透明度、激活状态、排序、对象数量、最终实体绑定和适用的输入门控，按实际动画约定配置容差及有界结束时间。固定等几秒、只检查横幅或只看到事件日志不算牌张动画通过。

动画不能成为业务副作用来源：播放/重播/取消不得自行发起出牌、扣费或重复提交。动画快进只能影响表现时间，不能延长或重置权威deadline。逻辑输入锁与最终物理键鼠/触屏焦点测试分别取证。

现有 ConfirmedAnimationQueueTests 提供 T1 队列基础；TablePlayModeTests 已有基线重置、私有动画取消及交互回归，但包含横幅断言，不等于上述全部实际牌张运动已覆盖。未实现的视觉效果登记为 NOT_IMPLEMENTED，未跑为 NOT_RUN，不能以队列或横幅绿灯补齐。

EditMode 保留资源/场景静态装配检查；UTF测试Player可补平台动画行为，但它仍属于T3证据，不代替普通交付包T4验收。

## 5. T4：最终端到端

### 5.1 候选与操作入口

冻结一份源码及生成输入清单，构建对应服务端和每个目标平台的完整客户端包。Windows各场景运行同一个完整包；Android各场景运行同一个APK。不同平台允许不同二进制，但必须绑定相同候选和各自适用的配置/资源/插件哈希。单独一个exe哈希不证明整个包相同。

通过实际鼠标/键盘或ADB/设备触屏操作普通游戏入口，不由C#测试脚本直接调用Presenter/Session来冒充用户操作。使用当前产品允许的配置；需要确定性局面的真实场景必须记录受控来源，不得执行中改权威终态或把测试Player当普通包。

本地模式走Unity进程内真实LocalHost；远端模式必须是普通客户端实际连接的真实服务。当前Unity默认工厂仍是本地路径，整场另有显式测试开关；没有对应普通产品入口的远端/整场项应保持缺口，不能设计即算实现。

## 10. 控制重复和测试膨胀

### 10.1 一个风险有一个主要证明位置

以“风险 + 前置状态 + 触发边界 + 核心断言”识别测试目的。新增测试前查已有覆盖映射：同一被测实现、相同输入等价类和相同断言已有稳定测试时，优先补参数或修正原测试；出现不同适配器、渲染机制、平台输入或真实故障边界时，才增加对应测试。

跨层保留的是新增风险的证明。例如“立直费用只扣一次”在T1证明规则、T2证明丢回执重连后仍只扣一次、T3证明重播不发命令、T4证明双击只提交一次；四者不能互相替代，但不需要四层各自重复全部立直合法性参数。

同一路径因不同花色、座位或实体ID产生的等价输入，不自动展开全部组合。只有它们改变来源方向、授权关系、庄闲支付、布局或实现分支时才选代表；同一规则由独立实现承载时，各实现仍需自己的合同验证。

### 10.2 用边界和交互选择场景

- **规则参数化：** 余额取费用前一单位/恰好费用/后一单位；时间取到期前/恰好/到期后；容量取上限内/恰好上限/首次超限。参数行分别计数，但共用准备代码。
- **按业务相互作用组合：** 优先覆盖千术预留×候选移动、立直×鸣牌、加杠×抢杠、换局×旧请求等有因果关系的组合。无相互作用的维度不做笛卡尔积；两两组合可用于一般配置抽样，已知三方竞争仍写明确场景。
- **按实现机制选代表：** 公用动画播放器的取消验证一组代表；某个动画有自己的对象池或回调时再增对应样本。存储、平台或生命周期机制不同，则保留独立用例。
- **短序列不变量：** T1可增加固定种子的合法操作序列，逐步检查136守恒、余额、终态及版本不变量，补充难以列尽的组合。种子数和步数有界；记录种子与完整动作，失败缩减为最短可重放序列，并沉淀一个确定性回归。随机探索不替代明确规则样本。
- **少量跨层连接：** T2验证规则结果到协议投影，T3验证事件到对象，T4验证真实输入到业务/画面；连接样本按不同数据路径选择，不按全部低层用例一比一复制。

共享夹具只负责构建合法初态和记录事实，不能让测试调用被测计分/规则代码生成唯一预期。一个执行旅程可以承载多个独立断言，但应报告各自检查点；前置失败后的未达分支记未跑，不能用一个大PASS替代分支结果。

### 10.3 场景与环境矩阵分别管理

Windows和Android各保留基础业务覆盖及平台特有场景。DPI、屏幕比例、系统版本、ABI和内存档位按声明范围与风险选择组合，不把每个业务场景乘上全部环境；布局、输入、生命周期、裁剪或运行时差异涉及的代表场景，才在相关环境扩展。原Windows32项、Android固定矩阵和明确要求全量执行的环境不由抽样规则缩减。

测试数据、业务场景和覆盖目标可以复用，平台结果独立统计。长时间运行、压力、兼容、隐私等专项沿用T1—T4载体及共同监督器，不单独复制登录/建房/断言框架。将这些测试打上风险标签即可，不为分类数量增加测试工程。

## 11. 增量维护与执行频率

先建立轻量覆盖清单，记录`coverageId → 现有caseId/文件 → 关键断言 → 主责层 → 所需跨层或平台证据 → 状态`。状态区分已实现、待补断言、待真实适配器/平台证据和待实现；实际运行结果另按候选记录。不通过删测试来制造精简，只有证明等价且保留全部有效断言、黄金来源及原验收映射后，才合并重复项。

| 执行时机 | 选择原则 |
|---|---|
| 本地修改反馈 | 相关T1、最小T2合同回归；表现改动运行相关T3 |
| 提交验证 | 依赖影响范围内的必需测试及相关P0回归；改动协议/存储时加入真实适配器路径 |
| 定期或专项 | 有界长序列、持续运行、压力及扩展设备/显示矩阵；周期由执行环境配置，不默认新增定时任务 |
| 冻结候选验收 | 必需T1/T2/T3和Windows/Android合同集合；普通包、同候选身份及逐项证据完整。被合同列为必需的专项不因平时低频执行而豁免 |
