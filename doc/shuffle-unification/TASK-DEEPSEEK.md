# 统一码牌千术：DeepSeek 开发任务与 Codex 验收契约

状态：**已实现，待独立验收**。主设计见 [DESIGN.md](DESIGN.md)，真实样本与未达标项见 [SIMULATION-RESULTS.md](SIMULATION-RESULTS.md)。本文件是实施约束；样本百分比不是正式 10,000 对标定，也不是产品保证。

## 交付目标

把准备阶段的「偷天换日」与「瞒天过海」合并为一次选择、一个目标、一次扣费的码牌千术。该目标同时作用于起手发牌和本局全部正常顺位预计摸牌槽。加入简单的目标感知 AI 及可复现的成对蒙特卡洛试验，按每名有效施术者报告相对不施术的单局和牌率。有效施术人数为 1、2、3、4 时，目标倍率分别为 2.50、1.75、1.50、1.00；四人档必须在相同种子下与基础洗牌逐张相同。

## 领域与线路契约

1. `ShuffleSelection`、协议 `ProtocolShuffleSelection`、客户端 `ShuffleSelection` / `ShuffleSelectionView` 只保留 `target: ShuffleTarget?` 与 `seeThrough: Boolean`。`target=null` 表示不做牌。所有旧 `initialTargets` / `drawTargets` 生产字段、UI 入口、AI 候选与测试都迁移；新协议解码严格拒绝旧字段，不恢复旧 TCP/V3 兼容壳。客户端只传目标枚举，不传牌山或未来信息。不可变快照继续防御性复制。
   这是不兼容的业务 DTO 变更；当前业务协议为 v7，实施时须同步提升 `ApiProtocol.PROTOCOL_VERSION` 与 `TcpWire.BUSINESS_VERSION` 至 v8，并保留双端旧业务版本显式拒绝与 `VERSION_MISMATCH` 验证。MJ-TCP/1 固定帧头的 wireVersion 仍为 1。
2. 目标收费暂定 30 点，看破 10 点，可叠加为 40 点；跳过 0 点。权威端从方案重算费用，保持预留、重试幂等、超时默认、扣费账本语义。AI 自动方案只选一个目标，且遵守 `aiMaySpend`、预算及看破权限。看破命中后取消被看破者的**全部**码牌效果，并保留清除落汗；收费仍按原提交方案。`n` 在看破抵消后按仍有效的目标方案计数，不能按曾付款人数计数。
3. `ShuffleConfig` 默认 `plannedDraws=18`，保留 0..18 的显式试验配置；生产默认覆盖 53..121 中本座位的全部 17/18 个预计槽。保留可配置强度与干扰系数；人数档位的强度和起手/摸牌成功交换额度应成为可命名、可测试、可调的独立配置，不能把胜率倍率直接乘在单张概率或结算结果上。配置须在领域层，协议/客户端房间配置映射按需同步。
4. 不新增三人麻将规则；`n=3` 指四人桌上三人施术。四人均有效时，生成器仍按同种子构造基础洗牌，但不进行任何交换。`seeThrough` 本身不计入 `n`。

## 牌山算法

1. 从 `TilePool.buildStandardSet()` 与局种子生成 136 张基础洗牌；方案按 seat 规范化，输入顺序不影响结果。每席只有一个 34 维需求向量；计算一次 `p_i = s_n / (1 + lambda * sum_{j != i}(s_n * cosine(d_i,d_j)))`，`lambda` 默认 0.65，结果限于 [0,1]。
2. 起手只优化本人的 0..52 槽，随后锁定全部起手槽。摸牌只优化本人的 53..121 正常顺位预计槽；随机打乱各席候选槽，让首尾均有非零受益机会。起手和摸牌各有**每席成功交换**额度 `B_initial(n)` / `B_draw(n)`，失败尝试不耗额度。初始单人试验档为 `s_1=.75, B_initial(1)=3, B_draw(1)=4`，需通过实测调参，不得声称已经达到 2.5 倍。
3. 只选 `U(donor,H)>U(current,H)` 的供体，按正收益平方加权确定性抽样。目标效用覆盖三色清一色、大三元、国士、大四喜。评估摸牌时用 13 张左右的虚拟手牌并确定性虚拟弃牌，不把过去全部摸牌永久累加。供体不能来自已提交槽、王牌 122..135、摸牌阶段的已发起手区，也不能来自本人尚待处理的目标槽。借用其他施术者尚待处理槽时需保证其目标效用不下降；可采取更保守的完全禁止借用规则并记录对多人倍率的影响。仅交换原有 `Tile` 实体，保持每张 `copyIndex`、赤五和 136 张闭环。
4. 发牌后不改牌山。鸣牌、杠牌、提前终局会使实际摸牌序列偏离预排槽位；UI 文案不得承诺每次摸牌必得目标牌。

## 目标感知 AI 与试验

1. 实现三个确定性的 `AIStrategy`：`SuitGoalAi(suit)` 用于三色清一色、`HonorTripletGoalAi(requiredHonors)` 用于大三元/大四喜、`KokushiGoalAi` 用于国士。输入限 `PlayerView` 和 `legalActions`，只读本人可见手牌及公共信息。优先接受合法自摸/荣和；清一色优先弃异色、只作有益的同色鸣牌；字牌刻子目标优先保留/碰缺口目标字牌；国士优先十三种幺九、跳过九种九牌流局、避免无益鸣牌。任何返回动作都必须属于 `legalActions`；无动作返回 null。目标优先选择不应绕过权威 deadline。
2. 建立可运行的成对全局模拟入口，固定种子、座位/庄家轮换和对手策略。每对仅改变施术/不施术，双方使用**同一个**目标感知 AI；另报 Basic AI 敏感性结果。统计每名施术者的任意役单局和牌率、指定役和牌率、流局率、平均点棒变化、目标牌保留及副露。按 6 目标及 `n=1..4` 分项；多人既测同目标也测异目标。输出种子范围、样本数、点估计和成对 95% 区间。可先用小样本烟测，正式标定每格至少 10,000 对；低频役追加样本直至区间有解释力。
3. 用标定结果调整人数档位，必要时按目标单独设置额度/强度，并记录每个参数的实际结果。倍率是统计设计目标，不是每个目标与任意对手配置的数学保证。若物理约束或数据使某格不可达，明确写出未达标及区间，不改结算胜负、不伪造测试数据。`n=4` 的牌山恒等是硬性验收项。

## 验收与报告

- 单测：目标唯一性与费用、看破整效抵消、无方案基础洗牌恒等、四人档逐张恒等、方案排序无关、固定种子复现、136 实体及王牌不被交换、起手锁定、尾段可受益、多人同/异目标、AI 合法动作和国士九种九牌行为。
- 跨层：协议 JSON 严格编解码与旧字段拒绝、server/client 映射、准备 UI 只显示单目标及准确价格、TCP/进程内提交与重放原子扣费。更新所有依赖旧字段的现有测试。
- 执行 `./gradlew test`、`./gradlew :android:assembleDebug`；若桌面 UI 改动影响布局，跑现有 GL 冒烟。报告命令、通过数、失败与未跑项。长时 10k 成对矩阵可作为独立离线任务，但必须提供可执行入口和**真实已运行的样本及结果**，不得把短跑数字称作正式标定。
- 保持七模块依赖边界及权威队列/控制代次。不要修改无关玩法、提交 git commit、推送或合并。交付改动清单、实测表、已知缺口，交 Codex 独立检视；发现问题后在原任务会话返工。
