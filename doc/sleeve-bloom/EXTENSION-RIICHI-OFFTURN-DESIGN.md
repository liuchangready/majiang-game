# 袖里藏花：立直与他家回合扩展设计

日期：2026-10-20。状态：**已实现并通过本轮自动化验收**（见[扩展验收](ACCEPTANCE-RIICHI-OFFTURN.md)）。本文补充[现行袖里藏花设计](DESIGN.md)，覆盖 engine 至表现层。现行代码已允许本人摸牌后的即时施术（含立直）、他家回合 `windowId` 预定与独立 10 秒权威截止；活牌山锁定/预留由 `GameState` 的可用槽位原语与 `TileMovement` 交付路径共同表达，不把本文当作未上线设计。旧设计中与本文冲突的使用时机、立直锁定、单一挂起 offer、超时及 UI 条款，以本文的扩展目标为准；原有费用、岭上次张规则、第四杠限制、136 张守恒、请求幂等和隐私约束继续有效。

## 用户确认的玩法与术语

1. 已立直的真人玩家也能施展袖里藏花。看到两张候选后先决定保留哪张；实际入手的牌若可自摸和牌，再由玩家选择和牌或继续。不能仅凭预览牌在尚未摸牌时和牌。
2. 本人弃牌后，直到本人下一次实际摸牌前，可在他家行动期间支付额度、预览两张牌并二选一。选中的实体牌为本人**下一次正常活牌山摸牌**预留，到摸牌时才入手。未选中的牌立即恢复为普通牌山牌，可被后续合法摸牌取走。本人本回合摸牌后的即时二选一保留。
3. 立直后的「加杠选择」按当前立直规则解释为**合法暗杠选择**：选中的摸牌若能构成暗杠，且 `RiichiKanValidator` 判定待牌和结构不变，可选择暗杠。真正的加杠要求已有碰牌副露，仍只对未立直玩家开放。暗杠成立并摸到新的岭上牌后，可再次支付 10 额度施展袖里藏花；每次成功激活各扣 10。
4. 费用按现有 `SLEEVE_BLOOM` 配置固定为 10。展示候选的成功激活即扣费；二选一、预留牌交付、自摸或杠选择不再扣费。杠后**再次激活**才扣第二笔。候选已揭示后，超时、提前流局、其他玩家和牌或本人未等到正常摸牌均不退款。

上文的「下一次正常摸牌」是必要的来源边界：他家回合预览的两张牌来自活牌山，不能把它们伪装成未来可能出现的岭上牌。如果本人先通过鸣牌进入吃碰后的出牌、或宣告大明杠获得岭上牌，预留保持到下一次正常摸牌；若该局没有这样的摸牌，终局清除预留。预留牌不参与中途的鸣牌或岭上补牌。UI 须明确显示「已选牌，待本人下次普通摸牌」，不能提示为下一次任意补牌。

## 三种施术路径

| 路径 | 激活窗口与两张候选 | 选择后的牌 | 本次摸牌计数 |
|---|---|---|---|
| 即时普通摸牌 | 本人 `CHEAT_WINDOW`；当前 `drawnTile` 与活牌山次张 | 沿用原规则，第二张换入 `drawnTile`、原摸牌退到次张槽 | 本次最多激活一次；立直也允许 |
| 即时岭上补牌 | 本人 `CHEAT_WINDOW`；当前岭上 `drawnTile` 与下一张未取岭上牌 | 沿用原规则；第四杠后无候选，拒绝且不扣费 | 本次补牌可另付 10；不继承上一普通摸牌的使用标记 |
| 他家回合预定 | 本人已弃牌后、他家行动期间；激活时活牌山最前方两张**未预留**实体牌 | 两张先临时锁定以完成选择；选中牌留在活牌山预留账本，另一张解锁；本人下次普通摸牌交付选中牌 | 预定成功交付的这次摸牌视为已施术，不能再即时激活 |

他家回合的入口允许在他家 `DRAW`、`CHEAT_WINDOW`、`DISCARD`、弃牌响应和抢杠响应期间提交，但它只改变施术者的私有预留状态，**不**替代或延迟当下玩家的合法动作、响应优先级或计时。最后一张活牌尚未被消耗、候选中有两张可用且本局未终结时才能激活。服务端每桌串行队列按已提交顺序裁决；激活早于一次摸牌则先锁定候选，晚于摸牌则按新牌山重新取候选。终局、准备、暂停、托管、观战或失去真人控制时均不可首次激活。

每座最多有一个他家回合的待选择 offer 或已选预留；同座不可重叠，也不能在本人有即时 offer 时预定。不同座可以预定，候选始终从未预留的活牌山取。原有「同一次取牌袖里藏花与偷梁换柱二选一」继续有效：预留牌真正交付的那次普通摸牌已经占用袖里藏花资格，偷梁换柱不能在该次摸牌激活；更早或之后的取牌不受影响。落汗仍可在其自身合法窗口独立使用。

## 他家回合的预留与 136 张守恒

**激活**在一次权威事务内校验身份、窗口、余额、两张未预留牌和本座唯一性，扣 10、记录使用请求并生成私有 offer；两张候选牌面只发给施术者。offer 选择结束前，两张候选均作临时锁定，其他摸牌和杠的补充抽取须跳过它们。临时锁定不改变牌的物理归属，仍属活牌山。

**选择**仅接受该 offer 的 `FIRST` 或 `SECOND`，不再次扣费。选中实体转为 `reservedForSeat`，另一实体解除锁定，仍在原相对顺序的活牌山队列中。其他人的正常摸牌跳过所有锁定或预留实体；不允许把预留牌当作宝牌指示、岭上牌、补充王牌或偷梁换柱目标。公开快照不展示预留牌身份或归属座位；本人私有快照展示已选实体与「待下次普通摸牌」。

**交付**发生于本人下一次合法普通摸牌，取出的就是预留实体；直到交付前它仍占一张活牌山余额，交付时才从牌山移入 `drawnTile`，正常减少剩余张数、增加 `turnNumber` 并设置 `lastDrawKind = NORMAL`。这次摸牌的 `drawnTile`、摸牌来源、海底判定、役种与算分按交付时的实际状态处理；激活和选择本身不算摸牌、不改变首巡或一发。交付后移除预留记录，将该 `turnNumber` 标记为已用袖里藏花，再重建合法动作与决策。

现有 `[wallPointer, wallEndExclusive)` 连续区间无法直接表达被跳过的预留槽。实现必须让活牌山剩余队列、临时锁定和单座预留共同成为 `TilePool` 可审计的权威结构，或提供等价的无洞抽取原语；所有从头端正常摸牌、尾端王牌替补、海底/荒牌检测、候选查询和洗牌后初始化均走同一结构。不得只在 UI 隐藏候选或单纯递增指针跳过预留牌，否则会丢失物理实体或使他家误摸。`wallRemaining` 统计尚未真正取出的普通牌，含预留牌；另需区分对当前抽取者可用的牌数。若轮到一位玩家摸牌而没有对其可用的活牌，应先按权威规则结束本局并清理预留，不得卡住队列、跨局携带或从预留牌偷取。杠所需的牌山尾端替补也必须有可用实体，否则该杠不提供为合法选项。

offer 二选一在他家行动期间不阻塞全桌。建议使用独立、权威的短选择截止（默认 10 秒，配置只控制时长，不影响单座行动时钟）；截止未选时默认 `FIRST` 并保留第一张，费用不退。若本人下次普通摸牌先于选择请求到达，同桌队列在该摸牌之前立即按 `FIRST` 结算 offer，再交付该牌，不等待选择倒计时、也不额外扣费。超时选择与其他摸牌并发时以同桌串行顺序为准：已锁定的两张在选择结算前不被他人取走。暂停冻结选择剩余时间；断线或托管不清除已付款 offer，恢复真人控制且未截止者可继续选；截止后服务器自行选 `FIRST`。局终释放所有临时锁定和预留，费用不退；牌仍在对应牌山区域直到该局物理结算完成，不可凭空删除。

## 立直后的候选、和牌与杠

即时施术在玩家确定摸牌来源之后、立直自动摸切之前执行。已立直不再构成 `SLEEVE_BLOOM_RIICHI_LOCKED`；若有余额和合法次张，客户端显示入口，权威保留完整原决策截止。`checkRiichiAutoDiscard` 不能在可施术的真人刚摸牌后立即抢先摸切；玩家明确选择摸切、选择和牌或合法暗杠，或者权威截止后才自动推进。没有可施术候选或余额时，原自动摸切行为仍可执行。动画不得延长权威时钟。

两张候选的「可胡」提示必须按各候选**假设成为实际 `drawnTile`**后的完整手牌，分别调用现有合法和牌与算分路径计算，含振听/役种/宝牌/海底/岭上和一发状态。预览结果只在本人私有 offer 显示；它不是可提交的和牌动作。玩家选定一张后，以真实换牌或预留交付结果重新生成 `DeclareTsumo`：合法时提供「和牌」和「继续」选择，不能自动和牌，也不能允许选另一张牌的预览来胡。选择继续后，立直玩家只可摸切实际保留牌或执行合法暗杠；选择和牌则正常结算。两张都可胡时，各自独立预览并按最终所选牌计算得点。

「可杠」也按最终保留牌重新算，不承诺预览即最终合法。立直后仅当摸到的实体参与四张同种牌、门清且 `RiichiKanValidator` 验证待牌和结构不变，才提供 `CLOSED_KAN`；不生成 `ADDED_KAN`。未立直玩家可按既有规则选择实际 `ADDED_KAN`，抢杠窗口仍优先裁决。玩家选择杠后若成立，按原有杠宝牌与岭上补牌时机进入新的 `CHEAT_WINDOW`：新的补牌有新的 `turnNumber` 和费用检查，可再次激活袖里藏花并再扣 10。若第四杠后没有下一张岭上候选，则第二次激活被拒且不扣费。被抢杠、杠不成立、余额不足、候选不足都不能扣第二笔。先前已付款的施术不因后续杠失败而退款。

## 七模块接线

| 层 | 必须补充的设计与实现责任 |
|---|---|
| engine | `GameState` 保存每座他家回合 offer/预留、来源、截止与使用归属；`deepCopy`、事务回滚、局终重置和 `StateInvariants` 覆盖 136 实体、锁定集合不交叉、offer 候选位置、每座唯一性。重构活牌山抽取以跳过预留；新增强类型激活/选择与预留交付领域入口。即时入口解除立直锁定；合法动作按最终入手牌重算；立直自动摸切让位给技能选择，超时顺序确定。计时与积分流水同事务提交。 |
| protocol | 增加他家回合预定的请求种类及 `FIRST/SECOND` 选择，明确 `roundId`、`windowId`、`offerId`、`controlEpoch`、`requestId`；即时请求继续使用现有 `decisionId`。私有 DTO 区分 `IMMEDIATE`、`OFF_TURN_OFFER`、`RESERVED` 与交付状态，含两候选、费用和权威剩余时间；仅即时 offer 可携带依当前局面计算的可胡/可杠预览，预定牌交付后从新决策生成真实选项。字段互斥与身份校验纳入 MJ-TCP/1 编解码，公开 DTO 不暴露牌面。协议版本按新增业务语义演进，旧端不得把未知状态误当成可操作即时 offer。 |
| server | `ServerTableHost` 将预定激活、选择、超时、普通/岭上摸牌、响应和结算串行裁决；授权以连接绑定座位为准，不信客户端自报座位。`RequestScopeReceiptStore` 对激活和选择请求保证副作用只执行一次，交付由单局状态机的一次正常摸牌事务保证只执行一次；回执重放不能重新扣费，窗口失效或不同载荷同 ID 拒绝。`TcpTableServer` 与 `InProcessBinding` 使用同一入口；重连推送完整私有 offer/预留，观战和他家仅看脱敏状态。 |
| client | `client.api` 新增强类型预定请求、选择请求与只读视图；接收有序完整快照驱动 `OFF_TURN_OFFER → RESERVED → 已交付/清理`，不靠回执猜测牌山。刷新 `windowId`/`offerId`/`controlEpoch` 时清掉旧选中，未知结果按现行 TCP 对账，不自动以新 ID 重施术；同一 offer 的选择可安全重放。即时模式和预定模式分别构造请求，但共用在途动作门控。 |
| presentation | `GameScreen` 他家回合可显示可用入口，激活后两牌模态仅锁本人技能输入，不阻断他家动画和行动；选完显示「已预定下次普通摸牌」和所选牌，实际交付时更新本人摸牌槽。立直即时窗口先展示二选一，选定且实际可胡时展示「和牌/继续」，可暗杠时展示「暗杠/摸切」；杠后新补牌再次显示可收费入口。菜单秘籍、中文原因码、倒计时、Esc 默认 `FIRST`、触控与 1280×720 / 960×540 布局同步修改。仅依赖 `client.api`，不读 engine 牌山。 |
| lwjgl3 / android | 薄启动壳不放规则；两端检验他家回合入口、立直选择、触控和断线恢复，沿用同一 `MahjongGame` 组合根。 |

他家回合可能没有属于施术者的普通决策，所以预定请求**不能**复用他人的 `decisionId`。`windowId` 应由权威在本人每次弃牌后签发，绑定本局、座位和该次弃牌后的时段，直至本人下一次实际摸牌或局终失效；控制代次另校验。offer 的选择使用 `offerId` 和当前私有快照身份，独立选择截止。所有余额与牌面校验由 engine 执行，server 在同桌队列内做绑定与幂等。选择 `FIRST`/`SECOND` 只改变本人未来摸牌的实体，不额外发牌或跳过原本应有的出牌。

## 验收矩阵

| 场景 | 必须观察到的结果 |
|---|---|
| 他家回合预定 | 本人弃牌后在三家任一行动/响应阶段可以激活、立即扣 10 并私见两张；他家摸牌跳过锁定/选中牌；本人下一次普通摸牌取得所选实体，未选实体可照常被摸。跨座连续预定、同座重复与并发抽牌按队列顺序正确。 |
| 立直即时施术 | 首次与杠后补牌均可施术；只允许摸切实际入手牌，换牌后的听牌/和牌/得点按实际牌计算；两张中仅一张可胡时可选该张和牌，也可选另一张继续；立直自动摸切不得抢先结束技能窗口。 |
| 杠后再次施术 | 立直暗杠只在待牌不变时开放；未立直加杠仍经抢杠；新岭上补牌再次激活另扣 10，总计 20，第二候选仍为下一岭上牌。第四杠、余额不足或被抢杠时不产生第二笔费用。 |
| 物理与边界 | 每一事务前后 136 张唯一归属；活牌山含预留牌的余量、当前可抽取数、岭上指针、王牌有效 14 张和指示牌一致；尾端替补不偷取预留；无可抽取牌时不死锁；局终、连庄、暂停恢复与回滚不遗留预留。 |
| 安全与恢复 | 两候选、所选预留和胡/杠预览仅本人可见；旧连接、观战、托管及他座伪造请求拒绝；相同请求重放只返回原回执，重连保留已付费 offer/预留与原截止，控制权变化不增加时间或重复扣费。 |
| 两端 UI | 他家回合边看他人操作边选牌；选择后明确「待下次普通摸牌」；实际摸牌后可胡/暗杠/摸切顺序正确；双视口桌面 GL、Android 构建及真机触控/网络实测分别记录，不把未做的实测记为通过。 |

实施顺序：先冻结 engine 的预留牌物理模型和超时/荒牌规则，再完成 protocol 与 server 的强类型请求及私有快照，随后接 client 状态机与表现层；最后做领域、TCP/进程内、UI 全链路验收。本文只交付设计，代码与验收需另行实施。
