## 优先修复的问题

### 1 P1 缺字段请求会终止整个 UDP 接收线程

位置：[ApiMessage.kt](../../protocol/src/main/kotlin/com/majiang/transport/api/ApiMessage.kt) 的 `decodeRequest`（134 行），[UdpTableServer.kt](../../server/src/main/kotlin/com/majiang/server/udp/UdpTableServer.kt) 的 `receiveLoop`（153 行）及 `handleSessionReq`（485 行）。归属：共享协议编解码与 T4。

已绑定客户端发送合法 JSON `{"api":"SNAPSHOT"}`，Gson 不执行 Kotlin 构造参数检查，得到 `requestId=null`。`getCachedResponse(request.requestId)` 抛出 NPE；接收循环没有隔离 `handleFrame` 的异常，唯一 Receiver 线程退出。随后新的 PING 也收不到 PONG，影响该服务器的全部房间。

独立用例 `malformedBoundRequestMustNotKillServerReceiver` 复现了完整 NPE 堆栈及后续收包超时。修复应同时包含解码后的显式字段验证和逐报文异常隔离；不能只捕获 JSON 语法异常。

### 2 P1 分片缓存会混合不同连接的报文

位置：[Fragmenter.kt](../../protocol/src/main/kotlin/com/majiang/transport/udp/Fragmenter.kt) 的 `inFlight`（146 行）、查找（221 行）、组包（267 行）。归属：T3，共享 protocol。

重组仅以 `msgId` 为键，未验证后续分片的 connectionId、原始类型和分片总数。不同 JVM 的消息计数器各自从头开始，正常多客户端就可能出现相同 msgId。服务器又共用一个 Fragmenter，因此连接 A 的第 0 片与连接 B 的第 1 片会拼成报文，并带上最后一片的连接身份。

`fragmentsWithSameMessageIdFromDifferentConnectionsStayIsolated` 已复现跨连接拼接。应按连接及消息隔离重组上下文，未绑定的 connectionId=0 还需要按来源端点隔离；校验分片元数据一致性。这项不能沿用之前 T3 单连接组件测试的通过结论。

### 3 P1 建房响应丢失后的重传会再建一个房间

位置：[UdpTableServer.kt](../../server/src/main/kotlin/com/majiang/server/udp/UdpTableServer.kt) 的 `handleLobbyReq`（315 行起）。归属：T4。

初次 CREATE_ROOM 使用 connectionId=0；若响应丢失，客户端仍以 0 重发相同 requestId。服务端只把回执缓存到新 session，后续大厅请求不会查该缓存，于是分配新 roomId、connectionId 和 token。`lostCreateResponseRetryMustReuseRoomAndConnection` 用同一 socket、同一 requestId、同一 seq 重试，返回了不同房间。

大厅绑定操作需要按来源及 requestId 保存有界的在途状态与完成回执，并在绑定响应丢失时重放同一结果。JOIN_ROOM 和 RESUME_SESSION 也需要覆盖同类重试，避免重复占座或重复顶号。

### 4 P1 窗口外全量 PUSH 不能恢复客户端

位置：[UdpClientBinding.kt](../../client/src/main/kotlin/com/majiang/client/transport/udp/UdpClientBinding.kt) 的 `handlePushFrame`（284 行）。归属：T5，必要时协调共享协议标记。

服务端窗口外恢复发送 `fromCursor=snapshot.cursor` 的全量 PUSH；客户端却始终按普通更新调用 `PushSequencer.offer`，没有传入全量语义。用例给出本地 cursor=0、全量 cursor=10，客户端未应用任何更新，反而发送 RESEND。服务端若继续返回同一全量，就会再次触发缺口，形成恢复循环。

此外，PushSequencer 回调和 `when(result)` 分支都执行补发或全量查询，单次缺口会重复发请求。修复需要端到端明确全量标记，并只保留一个恢复动作发起点。

### 5 P1 房主主动离房会先收到 KICK 导致离房 Future 失败

位置：[UdpRoom.kt](../../server/src/main/kotlin/com/majiang/server/udp/UdpRoom.kt) 的 `leave`（385 行）与 `close`；[UdpTableServer.kt](../../server/src/main/kotlin/com/majiang/server/udp/UdpTableServer.kt) 的 LEAVE_ROOM 分支。归属：T4。

房主离房先调用 `room.close()`，向包括发起者在内的所有连接发 ROOM_CLOSED KICK；随后才返回离房 RSP。真实客户端收到 KICK 后关闭 ReliableRequestor，在途 `leaveRoom()` 异常完成，无法按生命周期契约回到未绑定大厅。

`hostLeaveMustCompleteReceiptAndKeepLobbyConnectionOpen` 已复现 IOException。应区分主动离开者的成功回执与其他成员的房间终结通知，并保留离开者的大厅传输状态。

### 6 P2 离房响应丢失后无法重放

位置：[UdpTableServer.kt](../../server/src/main/kotlin/com/majiang/server/udp/UdpTableServer.kt) 的 LEAVE_ROOM 分支（550 行）。归属：T4。

处理离房时立即从 `sessionsByConnectionId` 删除 session。即使随后把回执写入 session 缓存，重传仍无法路由到它：客户端在收到成功响应前仍携带旧 connectionId，服务端静默丢弃。`lostGuestLeaveResponseMustBeReplayable` 重发相同普通成员离房请求后超时。

需要保留有界的离房完成记录或终结连接回执，使响应丢失仍能恢复；不能在回执可靠完成前丢掉唯一查询入口。

### 7 P2 已绑定客户端仍接受 connectionId 为零的终结消息

位置：[UdpClientBinding.kt](../../client/src/main/kotlin/com/majiang/client/transport/udp/UdpClientBinding.kt) 的入站检查（197 行）。归属：T5。

条件 `currentConnId != 0 && frame.connectionId != 0 && frame.connectionId != currentConnId` 特意放过了零连接号。`boundClientMustRejectZeroConnectionKick` 向绑定 42 的客户端送入 connectionId=0 的 KICK，连接实际被关闭。这违反已绑定后的连接隔离，也让未绑定期消息影响当前会话。绑定握手例外应限定为对应的在途绑定响应，而不是允许零连接号的所有类型。

### 8 P2 停服通知永远发不出去

位置：[UdpTableServer.kt](../../server/src/main/kotlin/com/majiang/server/udp/UdpTableServer.kt) 的 `close`（853–874 行）与 `send`（663 行）。归属：T4。

close 先置 isClosed、关闭 socket，再调用 `sendKick(SERVER_SHUTDOWN)`；send 遇到任一条件就直接返回。真实客户端等不到 SERVER_SHUTDOWN，只能后续靠网络错误或超时退出。`serverShutdownMustSendDisconnectReasonBeforeClosingSocket` 在本机无丢包场景也超时。应先完成终结通知的发送阶段，再释放传输资源。

### T4 三项回环测试没有正确处理分片

[UdpTableServerSmokeTest.kt](../../server/src/test/kotlin/com/majiang/server/udp/UdpTableServerSmokeTest.kt) 的 request 辅助方法（90–99 行）默认 fragmenter=null，调用处也未传入。因此 `testFullLoopbackLifecycle`、`testIdempotentReqRetry`、`testResendPushHandling` 在首个建房分片响应处就超时，没有验证到它们声明的后续行为。

即便传入 fragmenter，predicate 已取出了完整帧却没有保存，返回原始末片后又重组一次，仍不正确。需要一次性重组并保存完整帧、按 requestId 匹配 RSP，同时保留穿插到达的 PUSH/KICK，避免请求辅助方法吞掉后续断言所需事件。不要靠放宽超时时间消除这些失败。
