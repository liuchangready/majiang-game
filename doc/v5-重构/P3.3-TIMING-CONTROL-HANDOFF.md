## 2. 控制消息与公开 API

所有控制消息进入同一 actor 有界 mailbox，使用控制保留槽位；调用线程/定时器线程不直接修改控制者、时钟或 pending。

| API | 语义 |
|---|---|
| `DisconnectAsync` | actor 内按单调时钟断线；IMMEDIATE_AI 自增 epoch，GRACE_THEN_AI 写 grace，TIMEOUT_ONLY 不设 grace/不托管。 |
| `ReconnectAsync` | 只恢复连接，**不自动收回**；takeover 保持 takeover、epoch 不变。 |
| `ExpireGraceAsync` | 校验 owner/round/controlEpoch/graceDeadline/recoveryGeneration；迟到回调不能托管新控制者。 |
| `RequestTakeoverAsync` / `ReclaimControlAsync` | 显式托管/收回，自增 epoch；旧 AI/玩家提交失效。 |
| `ConfigureControlPolicyAsync` | 只改未来断线策略；有断线席位时拒绝。 |
| `CaptureAiObservationAsync` / `CompleteAiAsync` | actor 内捕获只读观察；推理在 actor 外；单入口回 actor 复核。 |
| `TickAsync(TableTickRequest)` | 批量入口。恢复代次 >0 时 raw `AiSubmissions` 一律拒绝；合法批量必须使用 `TableTickRequest.WithAiDecisions(...)` 携带 actor 捕获的 `AiDecision`。 |
| `GetControlSnapshotAsync` / `GetTimingSnapshotAsync` | P3.2/复核用只读控制与计时视图。 |

控制变化成功后，若该 seat 的 controlEpoch 改变且有 pending，会用同一 decision key/候选重建 `PendingDecision`，只更新 `ControlEpoch`。

### 2.1 版本、事件、提交边界

- **Domain 状态**：state_version + event_seq + 回执；`ITableCommitPort` 成功后才安装/发布；拒绝/失败不推进。
- **控制权威**：独立 control_version、`TableControlEvent`、`ControlChanged` 发布；不推进 Domain 版本。可选 `ITableControlCommitPort` 先提交后安装，失败可重试；未配置时明确仅内存，不宣称持久化。
- **计时权威**：`OpenDecisionAsync` 保持 P3.1 兼容的 `Configured` seam，不推进 state/control version，不宣称持久化；P3.4 必须 checkpoint。
- **恢复**：安装已由恢复所有者验证的基线；控制基线可带显式 grace，规则 timing 使用显式 remaining/overdue。

## 3. 玩家、AI、tick 统一校验

- 玩家：ownerEpoch、roundId、decisionId、实际 deadline、expectedStateVersion、controlEpoch；严格控制基线恢复后还校验 `RecoveryGeneration`。
- AI 单入口：round/decision/controlEpoch、automated、paused、实际 deadline、候选；恢复代次 >0 时 observation 必须由当前 generation 捕获。
- AI 批量入口：恢复代次 >0 时 raw `AiDecisionSubmission` 无来源，拒绝；`TableTickRequest.AiDecisions` 必须携带 actor 当前 generation 捕获的 observation 对象。调用方不能只填一个 generation 字段冒充来源。
- tick：plan 时 timeout-first；**每个后续动作执行前重新读取单调时钟并重验**。前项慢 commit 后，后项 AI 若已到期则执行 timeout，再记录 AI `DeadlineExpired`；已成功前缀保留，失败项及后续不消费。
- 单项在 deadline 前已裁决并开始 commit 的语义不变；玩家在 deadline 或之后 `DEADLINE_EXPIRED`，timeout 由下一次 tick 提交。

### 3.1 恢复栅栏与 AI 观察

- `BeginRecovery` 自增 `recoveryGeneration`、清空 pending、清除 open timings，保留 reserve ledger。grace fence 仍校验 round/epoch/graceDeadline/generation。
- 控制基线恢复成功时置严格 fence：`TableCommandEnvelope.RecoveryGeneration` 必须等于当前 generation，否则 `STALE_RECOVERY_GENERATION`。
- AI observation 以对象引用登记到 `ConditionalWeakTable`；只有当前 generation 捕获的对象可提交。旧 `AiDecision`、旧 observation、手工构造 observation 均拒绝。同决策多次捕获都可提交，但 actor 串行消费，第一次接受后其余返回 `StaleDecision`。
- 弱表不保活完整 observation；generation0 不登记，避免正常对局无界保存历史手牌/候选。
- 未提供控制基线的 P3.1 legacy 恢复路径仍保留以兼容原 25 项测试：不启用严格玩家 generation fence，也不声明计时/控制恢复安全；新 P3.3/P3.4 恢复必须带控制基线。

## 4. 恢复账本与宽限

- `TableRecoveryTiming.SeatReservesMillis` 是四座 reserve 账本，包含无 pending 的 idle seat。
- 同 round/同 state 且无显式 reserve 时复用当前 reserve；跨 round/state 且带控制基线时缺省 reserve 拒绝 `RECOVERY_TIMING_INVALID`。
- `TableRecoveredDecision` 的 remainingBase/remainingReserve/overdue 按 base-first：`baseRemaining=max(0,base-overdue)`，`reserveRemaining=max(0,reserve-max(0,overdue-base))`，`deadline=now+baseRemaining+reserveRemaining`；超过配置、溢出、finished round、round/epoch 不符、重复 seat 均拒绝。
- `TableRecoveredGrace(seat, remainingGraceMillis, overdueMillis)` 用于断线且有 grace 的席位；actor 以本地 now 重建 `DisconnectedAtMillis=now`、`GraceDeadlineMillis=now+remaining`（overdue>0 时为 now）。持久化绝对 monotonic 不参与比较。
- 缺失 grace timing、对 connected/no-grace 席位多余 timing、grace deadline 溢出均拒绝；断线但无 grace 的席位仅重建 disconnectedAt=now。
- 旧 grace timer 由 round + expectedEpoch + graceDeadline + recoveryGeneration 四重 fence 拒绝。

## 5. P3.2 只读接口

- `TableControlSnapshot` / `TableSeatControlView`：控制者、连接、epoch、grace、policy、controlVersion、recoveryGeneration。
- `TableTimingSnapshot` / `TableSeatTimingView`：`DecisionTiming`、剩余 reserve、pending key、paused、recoveryGeneration；不含暗牌/牌山/种子。
- `TablePublicationKind.ControlChanged` 与 `Recovered`：提交/安装后发布，带控制快照。
- `CaptureAiObservationAsync` 是 AI 专用最小视图，不是按流投影；P3.2 仍从 Domain 构造白名单投影。
