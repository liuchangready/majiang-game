## 2. 控制消息与公开 API

所有控制消息进入同一 actor 有界 mailbox，使用控制保留槽位；调用线程/定时器线程不直接修改控制者、时钟或 pending。

| API | 语义 |
|---|---|
| `DisconnectAsync` | actor 内按单调时钟断线。`IMMEDIATE_AI` 立即自增 epoch；`GRACE_THEN_AI` 写 grace；`TIMEOUT_ONLY` 不设 grace/不托管。 |
| `ReconnectAsync` | 只恢复连接，**不自动收回**；`Takeover` 保持 takeover、epoch 不变。 |
| `ExpireGraceAsync(TableGraceExpiryFence)` | 校验 ownerEpoch、roundId、expectedControlEpoch、graceDeadline、recoveryGeneration；迟到回调不能托管新控制者。 |
| `RequestTakeoverAsync` / `ReclaimControlAsync` | 显式托管/收回，自增 controlEpoch；旧 AI/玩家提交失效。 |
| `ConfigureControlPolicyAsync` | 只改未来断线策略；有断线席位时拒绝。 |
| `CaptureAiObservationAsync` / `CompleteAiAsync` | actor 内捕获只读观察；推理在 actor 外；结果回 actor 复核。 |
| `GetControlSnapshotAsync` / `GetTimingSnapshotAsync` | P3.2/复核用只读控制与计时视图。 |

控制变化成功后，若该 seat 的 `controlEpoch` 改变且有 pending，会用同一 decision key/候选重建 `PendingDecision`，只更新 `ControlEpoch`。

### 2.1 版本、事件、提交边界

- **Domain 状态**：`state_version` + `event_seq` + 回执；`ITableCommitPort` 提交成功后才安装/发布；拒绝/失败不推进。
- **控制权威**：独立 `control_version`、`TableControlEvent`、`TablePublicationKind.ControlChanged`；不推进 `state_version/event_seq`。可选 `ITableControlCommitPort` 先提交后安装，失败/取消/旧版本不安装、可重试；未配置端口时明确仅内存，不宣称持久化。
- **计时权威**：`OpenDecisionAsync` 保持 P3.1 兼容的 `Configured` seam，不推进 state/control version，不发布 Domain/控制事件，也不宣称持久化；P3.4 必须 checkpoint `DecisionClock`/pending/reserve。
- **恢复**：安装的是已由恢复所有者验证的基线；控制基线可带显式 grace 重建，规则 timing 使用显式 remaining/overdue。

## 3. 玩家、AI、tick 统一校验

- 玩家：ownerEpoch、roundId、decisionId、实际 deadline、expectedStateVersion、controlEpoch；严格恢复后还校验 `RecoveryGeneration`。
- AI：round/decision/controlEpoch、automated、paused、实际 deadline、冻结候选；严格恢复/恢复代次 >0 时还要求 observation 在当前代次捕获。
- tick：plan 时按 timeout-first 排序；**每个后续动作执行前重新读取单调时钟并重验**。前项慢 commit 后，后项 AI 若已到期则改为执行 timeout，再记录 AI `DeadlineExpired`；已成功前缀保留，失败项及后续不消费。
- 单项在 deadline 前已裁决并开始 commit 的语义不变：不会因为 commit 期间时钟前进而回滚该已开始提交的项。
- 玩家在 deadline 或之后返回 `DEADLINE_EXPIRED`，零版本/零提交/零发布；权威 timeout 由下一次 tick 提交（tick-first 与 player-first 两种次序均有测试）。

### 3.1 恢复栅栏与 AI 观察

- `BeginRecovery` 自增 `recoveryGeneration`，清空 pending、AI 观察代次，保留 reserve ledger 并清除 open timings。
- 控制基线恢复成功时置严格 fence：`TableCommandEnvelope.RecoveryGeneration` 必须等于当前 generation，否则 `STALE_RECOVERY_GENERATION`；旧玩家命令不能污染新基线。
- 所有恢复后 AI 结果必须来自恢复后 `CaptureAiObservationAsync` 返回的 observation 对象；actor 以对象引用记录其 generation。旧 `AiDecision`、旧 observation、手工构造 observation 均拒绝；恢复后新观察可正常提交。
- 未提供控制基线的 P3.1 legacy 恢复路径仍保留以兼容既有 25 项测试：它不做严格玩家 generation fence，且不声明计时/控制安全；新 P3.3/P3.4 恢复必须带控制基线。

## 4. 恢复账本与宽限

- `TableRecoveryTiming.SeatReservesMillis` 是四座 reserve 账本，包含没有 pending 的 idle seat。
- 同 round/同 state 且无显式 reserve 时，actor 复用当前 reserve（不赠送时间）；跨 round/state 且带控制基线时缺省 reserve 直接拒绝 `RECOVERY_TIMING_INVALID`。
- `TableRecoveredDecision` 的 `remainingBase/remainingReserve/overdue` 按 base-first 扣减：`baseRemaining=max(0,base-overdue)`，`reserveRemaining=max(0,reserve-max(0,overdue-base))`，`deadline=now+baseRemaining+reserveRemaining`。超过配置 base/reserve、溢出、finished round、round/epoch 不符、重复 seat 均拒绝。
- `TableRecoveredGrace(seat, remainingGraceMillis, overdueMillis)` 用于每个断线且有 grace 的席位；actor 以本地 `now` 重建 `DisconnectedAtMillis=now`、`GraceDeadlineMillis=now+remaining`（overdue>0 时为 now）。持久化的绝对 monotonic 时间戳不参与比较。
- 缺失 grace timing、对 connected/no-grace 席位提供多余 timing、grace deadline 溢出均拒绝；断线但无 grace 的席位仅重建 `DisconnectedAtMillis=now`。
- 旧 grace timer 由 round + expectedEpoch + graceDeadline + recoveryGeneration 四重 fence 拒绝。

## 5. P3.2 只读接口

- `TableControlSnapshot` / `TableSeatControlView`：控制者、连接、epoch、grace、policy、controlVersion、recoveryGeneration。
- `TableTimingSnapshot` / `TableSeatTimingView`：`DecisionTiming`、剩余 reserve、pending key、paused、recoveryGeneration；不含暗牌/牌山/种子。
- `TablePublicationKind.ControlChanged` 与 `Recovered`：提交/安装后发布，带控制快照；P3.2 据此重建流基线并拒绝旧 binding/epoch。
- `CaptureAiObservationAsync` 是 AI 专用最小视图（本 seat 手牌、公开副露/牌河/宝牌、候选、deadline），不是按流投影；P3.2 仍从 Domain 构造白名单投影。
