## 2. 控制消息与公开 API

所有控制消息都进入同一 actor 的有界 mailbox，使用控制保留槽位；调用线程/定时器线程不直接修改 `ControlRegistry`、`DecisionClock` 或 pending。

| API | 语义 |
|---|---|
| `DisconnectAsync(seat, ownerEpoch, expectedControlEpoch, reason)` | 在 actor 内用单调时钟断线。`IMMEDIATE_AI` 立即自增 epoch 进入 `Takeover`；`GRACE_THEN_AI` 保留真人控制者并写 `graceDeadline`；`TIMEOUT_ONLY` 只记断线、不设宽限、不托管。 |
| `ReconnectAsync(seat, ownerEpoch, expectedControlEpoch, reason)` | 只恢复连接状态。**不自动收回**；若当前是 `Takeover`，重连后仍是 `Takeover` 且 epoch 不变。 |
| `ExpireGraceAsync(TableGraceExpiryFence)` | 迟到宽限回调。fence 同时校验 ownerEpoch、roundId、expectedControlEpoch、expectedGraceDeadlineMillis、expectedRecoveryGeneration；不匹配即拒绝，不能托管新控制者。 |
| `RequestTakeoverAsync(seat, ownerEpoch, expectedControlEpoch, reason)` | 显式托管；自增 epoch，废止旧 AI/玩家提交。 |
| `ReclaimControlAsync(seat, ownerEpoch, expectedControlEpoch, reason)` | 显式收回；自增 epoch，恢复 preferred human 控制器。 |
| `ConfigureControlPolicyAsync(policy, ownerEpoch, reason)` | 只改未来断线策略；任一 seat 处于断线时拒绝，避免在途 grace 语义变化。 |
| `CaptureAiObservationAsync(seat)` | actor 内生成只读 `AiObservation`；推理必须在 actor 外完成。 |
| `CompleteAiAsync(AiDecision)` | 结果回到同一 mailbox 后重新校验 round/decision/controlEpoch/实际 deadline/候选。 |
| `GetControlSnapshotAsync()` | P3.2 用的控制权威只读快照（含 policy、四个 seat、controlVersion、recoveryGeneration）。 |
| `GetTimingSnapshotAsync()` | P3.2/复核用的规则计时只读快照（deadline、reserve、pending key、paused、recoveryGeneration）。 |

控制变化成功安装后，若该 seat 的 `controlEpoch` 发生变化且存在 pending decision，会以**同一 decision key/候选**重建 `PendingDecision`，只更新其 `ControlEpoch`。因此旧 epoch 的 AI/玩家提交被拒绝，新控制者可在同一决策上继续（受原 deadline 约束）。

### 2.1 控制版本、事件与提交边界

控制权威与 Domain 状态刻意分开：

- **Domain 状态**：`state_version` + `event_seq` + 回执；必须 `ITableCommitPort` 提交成功后才安装/发布。拒绝/失败不推进。
- **控制权威**：独立的 `control_version`、`TableControlEvent`、`TablePublicationKind.ControlChanged` 发布。控制变化不推进 `state_version` 或 `event_seq`，也不伪造 Domain 事件。
- **可选控制提交端口**：配置 `ITableControlCommitPort` 时，actor 先等待控制提交成功，再安装 `ControlRegistry`、推进 `control_version` 并发布；失败/取消/旧版本时不安装、不发布，可原样重试。未配置端口时，P3.3 只保留内存控制变化并发布 `ControlChanged`，**不宣称持久化**；P3.4 必须提供持久控制日志/检查点并以其版本初始化该端口。
- **计时权威**：`OpenDecisionAsync` 仍是 P3.1 兼容的 `Configured` seam：不推进 `state_version`/`event_seq`/`control_version`，不发布 Domain/控制事件，也不宣称持久化。P3.4 必须把 `DecisionClock`/pending/剩余 reserve 纳入检查点；P3.3 不把该 seam 冒充控制或状态提交。

`TableControlEvent` 携带控制变化所需字段：seat、前后 status/kind/epoch、grace deadline、断线时间、AI profile；策略配置事件另带 mode/grace/AI profile。这样 P3.4 的日志可以重建控制状态，而不是只记一个枚举。

## 3. 玩家、AI、tick 的统一校验

在 actor 消费点校验：

- 玩家命令：ownerEpoch、roundId、seat、decisionId（若 seat 有 pending）、实际 `now < deadline`、expectedStateVersion、当前 `controlEpoch`。
- AI 结果：roundId、decision key、当前 controlEpoch、seat 是否 automated、是否 paused、实际 `now < deadline`、动作是否仍在冻结候选内。
- tick：使用 actor 单调时钟一次性读取；先处理所有已到 deadline 的 timeout，再处理同 tick AI；`now >= deadline` 时 timeout 优先。

**玩家在 deadline 或之后的处理决定**：玩家命令返回 `DEADLINE_EXPIRED`，零版本、零提交、零发布；权威 timeout 由下一次 `TickAsync` 提交。不能用客户端动画延迟这一点。测试覆盖“玩家先到 deadline、随后 tick”和“tick 先提交 timeout、随后玩家找不到决策”两种队列次序；AI 在 deadline 边界由既有测试和新用例覆盖。

多座位响应窗口按 seat 分别持有 pending；同一 seat 只能有一个 pending。tick 可对多个 seat 的 due timeout/AI 逐项计划，已成功提交的前缀保留，失败项和后续项不消费 timing/pending。同 seat 的重复 AI 结果返回 `STALE_DECISION`，不会二次推进。

### 3.1 异步 AI 的调用责任

1. actor 内调用 `CaptureAiObservationAsync(seat)`；返回的 `AiObservation` 只含本 seat 手牌、公开副露/牌河/宝牌指示牌、分数、冻结候选、decision/epoch/deadline 和剩余 wall count；不含牌山顺序、种子、对手暗牌、里宝牌或完整 `TilePositionMap`。
2. 调用方在 actor 外运行 `IAiStrategy`/`AiDecisionService.ReasonAsync`，**不要**把 actor 的 `IAiAuthorityPort.Capture` 绑定到实时 actor；应使用上述异步捕获值。
3. 用 `CompleteAiAsync` 把 `AiDecision` 交回 actor。actor 重新检查上述身份和 deadline，再做 Domain 转移/提交。推理期间 actor 可以继续处理其他消息，不持有推理锁。

该观察是 **AI 专用最小视图**，不是 P3.2 的按流投影；公开/私有投影仍由 P3.2 从 Domain 状态构造。

## 4. 恢复边界

- `BeginRecoveryAsync`：推进 `recoveryGeneration`，清空 pending/timing，进入 `Recovering`；期间 tick、AI、控制副作用和 AI 观察全部拒绝。
- `CompleteRecoveryAsync(baseline)`：只接受 `Recovering`，校验 ownerEpoch/stateVersion/eventSeq 不回退；可选控制基线校验 `controlVersion` 不回退、每个 seat `controlEpoch` 不回退、同一 epoch 不允许静默更换控制器；可选 timing 必须带精确控制基线。
- `TableRecoveredDecision` 显式提供 `remainingBaseMillis`、`remainingReserveMillis`、`overdueMillis`。actor 用当前单调时间重建：
  `deadline = now + max(0, base + reserve - overdue)`。
  不使用本机 UTC，也不把另一进程的持久 monotonic 值直接相减；溢出、round 不符、epoch 不符、重复 seat、finished round、无控制基线等均拒绝安装。
- 安装后旧 round 的 AI 由 roundId 拒绝；旧 controlEpoch 的 AI/玩家由新控制基线或 fence 拒绝；旧宽限 timer 由 roundId + expectedControlEpoch + grace deadline + recoveryGeneration 拒绝。
- 未提供控制基线的 P3.1 legacy 恢复路径仍保留（既有 25 项测试），但禁止恢复 timing；它只保留当前内存控制，recoveryGeneration 仍使恢复前捕获的 grace fence 失效。P3.3/P3.4 的新恢复应始终带控制基线。

## 5. P3.2 需要的控制只读接口

- `GetControlSnapshotAsync()` → `TableControlSnapshot`：roomId/roundId/ownerEpoch/stateVersion/controlVersion/recoveryGeneration/policy/四个 `TableSeatControlView`。
- `GetTimingSnapshotAsync()` → `TableTimingSnapshot`：每个 seat 的 `DecisionTiming`、剩余 reserve、pending decision key、paused、recoveryGeneration；不包含暗牌/牌山/种子。
- `TablePublicationKind.ControlChanged`：提交成功后发布；含 `TableControlSnapshot`、一个或多个 `TableControlEvent`，无 Domain receipt/events。
- `TablePublicationKind.Recovered`：安装已持久化基线后发布，含控制快照；P3.2 应据此重建流基线并拒绝旧 binding/epoch。
- `CaptureAiObservationAsync` 是 AI 专用视图，不能替代按座位/观战投影；P3.2 仍须从 Domain 状态构造白名单投影。
