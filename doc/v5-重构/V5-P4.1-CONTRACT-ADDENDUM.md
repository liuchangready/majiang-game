### 1.2 存储模型选定：Checkpoint + Tail 模型
采用 **Checkpoint + Tail 模型（基础检查点 + 增量日志 + 事实与时序快照）**。
- **架构必然性**：
  1. 依据 [`TableActor.cs:3269-3358`](file:///D:/majiang-wt/p41-contract-addendum-anti-20261026/dotnet/src/Mahjong.TableRuntime/TableActor.cs#L3269-L3358)，权威 `TableActor` 在通常出牌、鸣牌、出千等业务提交时生成的 `TableDurableCommitRequest.Checkpoint` 均为 `null`，仅在终局（`terminal = true` / `nextState.IsFinished`）显式调用 `SaveCheckpointAsync` 时才构建全量 `TableCheckpoint`；
  2. 若强制采用 Pure Full Checkpoint 模型，每次命令提交均须将整桌 136 张物理牌、状态机、事件历史及出千账本全量序列化落盘，在移动设备与单机环境下将产生严重 I/O 阻塞；
  3. Checkpoint + Tail 模型以开局/局末的 `TableCheckpoint` 作为基线，局中命令仅增量追加 `CommandJournals`、`EventJournals`，并在单次原子替换中同步刷写最新的 `LatestTimingPayload` 与 `LatestCommittedFactsPayload`，既保证物理闭环与完整可恢复性，又维持了极高的运行时吞吐。

### 1.3 `LocalSave` 物理文件数据契约与所有权规范
单机存档文件 `<roomId>.save` 采用单文件二进制/JSON 复合信封，物理模型与状态行结构定义如下：

```csharp
namespace Mahjong.LocalHost
{
    public enum LocalSaveTerminalState : byte
    {
        InProgress = 0,
        RoundFinished = 1,
        MatchFinished = 2,
        Abandoned = 3
    }

    public enum LocalSaveOrigin : byte
    {
        Local = 0,
        Remote = 1
    }

    /// <summary>
    /// 核心权威状态行 (Canonical State Row)：所有版本号与状态哈希的唯一事实来源。
    /// 严格使用 Mahjong.Contracts 与 Mahjong.TableRuntime 既有强类型。
    /// </summary>
    public sealed class LocalSaveState
    {
        public StateVersion StateVersion { get; set; }
        public EventSeq LastEventSeq { get; set; }
        public ulong StateFingerprint { get; set; }
        public TablePayloadSha256 StateHash { get; set; }
        public long ControlVersion { get; set; }
        public ulong ControlEpoch { get; set; }
        public long TimingVersion { get; set; }
        public long CheatVersion { get; set; }
        public ulong CheatFingerprint { get; set; }
        public bool CheatBound { get; set; }
    }

    /// <summary>
    /// 单机完整持久化信封 (Proposed LocalSave Root Container)。
    /// </summary>
    public sealed class LocalSave
    {
        public int FileFormatVersion { get; set; } = 1;
        public string RoomId { get; set; } = string.Empty;
        public LocalSaveOrigin Origin { get; set; } = LocalSaveOrigin.Local;
        public int RulesetVersion { get; set; } = 1;

        // 核心权威状态行 (唯一版本来源，外层不重复声明状态/控制/时序/千术版本)
        public LocalSaveState CurrentState { get; set; } = new();

        // 基础检查点载荷与整块哈希 (CheckpointSha256 覆盖 BaseCheckpointBlob 全字节域)
        public byte[] BaseCheckpointBlob { get; set; } = Array.Empty<byte>();
        public TablePayloadSha256 CheckpointSha256 { get; set; }

        // 局中 Tail 增量时序快照
        public byte[] LatestTimingPayload { get; set; } = Array.Empty<byte>();
        public TablePayloadSha256 LatestTimingPayloadSha256 { get; set; }

        // 局中已确认事实快照 (可为空，空时回退至 BaseCheckpoint)
        public byte[]? LatestCommittedFactsPayload { get; set; }
        public TablePayloadSha256? LatestCommittedFactsPayloadSha256 { get; set; }

        // 控制快照载荷 (来自 Checkpoint.ControlPayload，外层无冗余数据源)
        public byte[]? CurrentControlSnapshotPayload { get; set; }
        public TablePayloadSha256? CurrentControlSnapshotSha256 { get; set; }

        // 增量日志与收据字典
        public List<TableCommandJournalRecord> CommandJournals { get; set; } = new();
        public List<TableEventRecord> EventJournals { get; set; } = new();
        public Dictionary<string, TableDurableReceipt> Receipts { get; set; } = new();
        public Dictionary<string, TableSettlementOutboxRecord> Outbox { get; set; } = new();

        // 终局状态元数据
        public LocalSaveTerminalState TerminalState { get; set; }
        public string? TerminalResultId { get; set; }
        public int? TerminalResultVersion { get; set; }
    }
}
```

- **版本所有权唯一性规则**：`StateVersion`、`LastEventSeq`、`ControlVersion`、`TimingVersion` 与 `CheatVersion` 唯一归属于 `save.CurrentState`，外部 `save` 容器严禁重复定义同名版本字段，避免产生双重权威。

   - `ControlVersion = save.CurrentState.ControlVersion`；
   - `BootId`、单调时钟 `CapturedMonotonicMillis` 与 UTC 时钟 `CapturedAtUtcMs` 完整从解码后的快照中还原。
4. **`LoadCommittedFactsAsync(string roomId, CancellationToken ct)`**：
   - 若 `save.LatestCommittedFactsPayload != null`，校验 `save.LatestCommittedFactsPayloadSha256` 并返回 [`TableCommittedFactsSnapshot`](file:///D:/majiang-wt/p41-contract-addendum-anti-20261026/dotnet/src/Mahjong.TableRuntime/TableDurableContracts.cs#L1442)；
   - 若为空，则返回 `null`（恢复流水线自动回退至基线 `checkpoint.CommittedFactsPayload`）。
5. **冷恢复时序推演全闭环（$t \to t+1 \to t+1 \to t+2$）**：
   - 设当前状态时序版本为 $t$（`save.CurrentState.TimingVersion = t`，`timingRow.TimingVersion = t`）；
   - 执行 `SaveCheckpointAsync`，传入 `checkpoint.TimingVersion = t + 1`；
   - 栅栏校验通过，持久化并安装 `save.CurrentState.TimingVersion = t + 1` 落盘；
   - 进程冷重启触发恢复，调用 `LoadTimingAsync`，组装返回 `timingRow.TimingVersion = t + 1`；
   - `TableRecoveryService` 校验 `timingRow.TimingVersion (t + 1) >= checkpoint.TimingVersion (t + 1)`，断言通过，无 `RecoveryTimingInvalid` 错误；
   - 恢复服务执行时钟对齐，调用 `AppendTimingAsync(..., expectedTimingVersion: t + 1)`，成功安装并持久化 `save.CurrentState.TimingVersion = t + 2`；
   - **恢复时序原子写回保障**：恢复服务在将 `TableActor` 发布为 `Serving` 状态之前，必须通过原子文件替换将调整后的 $t+2$ 时序原子写回磁盘 `<roomId>.save`，确保对外服务状态与磁盘完全一致。

### 1.5 单一提交安全边界、双分支原子文件流水线与故障裁决

#### 1.5.1 单一提交边界与安全不弱化保证
- **单一原子提交边界**：所有状态变更（已确认状态行、`CommandJournals`、`EventJournals`、`Receipts`、`Outbox`、`LatestTimingPayload` 及其哈希、`LatestCommittedFactsPayload` 及其哈希、`CurrentControlSnapshotPayload` 及其哈希、以及可选的 `BaseCheckpointBlob`）必须全部序列化至同一份磁盘文件，在单次原子替换（Move 或 Replace）中落盘。严禁部分落盘，严禁先更新内存后异步落盘。
- **不可弱化的安全底线**：
  1. `TableRecoveryOptions.RequireCommittedFacts` **强制保持为 true**；
  2. 136 张实体牌物理守恒律（`TableAuthority` 终局验证）不得跳过；
  3. 状态 Hash 校验、OwnerEpoch 租约 CAS 及版本栅栏全面生效。

#### 1.5.2 初次创建分支 vs 替换分支与提交点解耦
依据 Caller 真实文件故障探针 [`move-backup-failure.json`](file:///D:/majiang-wt/p41-contract-addendum-anti-20261026/artifacts/TEMP/caller-addendum-review-r2/move-backup-failure.json)，`File.Move` 成功后初始 `File.Copy` 可抛出 `IOException`。严格将**事务提交点**与**备份维护**解耦：

```mermaid
flowchart TD
    req["持久化请求 (Commit / SaveCheckpoint / AppendTiming / CommitControl / CreateRoom)"] --> f1["1. 栅栏校验 (Lease/Epoch/CAS/Consistency)"]
    f1 -->|校验失败| rej["返回失败，零磁盘变动"]
    f1 -->|校验通过| s2["2. 将内存候选完整状态序列化至临时文件 (<roomId>.save.tmp.<guid>)"]
    s2 --> s3["3. 执行 Flush / fsync 确保落盘并校验 SHA-256"]
    s3 --> fcheck{"4. 目标 primary 是否已存在？"}

    fcheck -->|否 (初次建房)| b_create["4a. 初次创建分支:<br/>File.Move(tmp, primary)"]
    fcheck -->|已存在 (替换更新)| b_replace["4b. 已有替换分支:<br/>File.Replace(tmp, primary, backup, true)"]

    b_create --> commit_point["★ 事务提交点 (Linearization Point) ★<br/>File.Move 或 File.Replace 执行成功即提交<br/>磁盘文件已具备权威事实"]
    b_replace --> commit_point

    commit_point --> b_copy{"初次创建分支: 执行初始备份 Copy"}
    b_copy -->|Copy 成功| s6["5. 内存正式安装并返回 Committed"]
    b_copy -->|Copy 失败 (如 IOException)| b_fail["标记 BackupNeedsRepair = true<br/>磁盘提交事实已确立，安装内存并返回<br/>下一次原子替换自动修复备份"]

    commit_point -.替换后取消/中断.-> post_cancel["已提交事实保留 (Receipt/Outbox)，冷恢复可重载，严禁当作未提交盲目重试"]
```

1. **初次创建分支（`File.Exists(primary) == false`）**：
   - 将初始数据写入 `<roomId>.save.tmp.<guid>` 并执行 Flush；
   - **执行提交原语**：`File.Move(tmpPath, primaryPath)`。**此调用返回成功瞬间即为事务提交点**；
   - **备份维护分离**：紧接着尝试 `File.Copy(primaryPath, backupPath, overwrite: true)`：
     - 若 Copy 成功：完成初始备份；
     - 若 Copy 失败（抛出 `IOException`）：**严禁回滚**，因为 `primaryPath` 已经合法持有持久化的已提交事实且收据有效。系统内部状态记录 `BackupNeedsRepair = true`，内存正常安装并返回 `Committed`，在下一次写入时由正常 Replace 自动补全备份。
2. **已有文件替换分支（`File.Exists(primary) == true`）**：
   - 直接调用操作系统原子替换原语：`File.Replace(tmpPath, primaryPath, backupPath, ignoreMetadataErrors: true)`；
   - 此原语在 Windows (NTFS/ReFS) 与 Linux 下具备底层原子性，成功后 `primary` 成为新版本，原 `primary` 自动降级为 `backup`（`<roomId>.save.prev`），`tmp` 自动消失。

#### 1.5.3 损坏主文件回退时的排他锁内安全原子发布
彻底杜绝非原子的原地 `File.Copy(tmp, primary)`。在已持有独占租约下采用“同卷隔离重命名 + 原子候选重命名”：
1. `File.Move(primaryPath, corruptPath)`（隔离损坏的主文件）；
2. `File.Move(tmpPath, primaryPath)`（将候选文件原子提升为主文件）；
3. `File.Delete(corruptPath)`（清理隔离文件）。
全程备份文件 `*.save.prev` 保持不动，安全防腐。

#### 1.5.4 文件原语故障与提交裁决矩阵

| 故障场景 | 发生时机与故障现象 | 磁盘实际状态 | 提交判定 (Commit Verdict) | 恢复与后续处理规则 |
|---|---|---|---|---|
| **场景 1：Move 前中断** | `File.Move` 执行前发生线程取消或 I/O 异常 | `primary` 不存在，仅有 `.tmp` | **未提交 (ABORTED)** | 删除 `.tmp` 文件；向调用方抛出异常；内存保持初始状态，零副作用。 |
| **场景 2：Move 成功备份失败** | `File.Move` 成功，后续 `File.Copy` 抛出 `IOException` | `primary` 已为新版本，无 `backup` | **已提交 (COMMITTED)** | 严禁回滚！`primary` 已为有效提交状态，安装内存并返回成功；标记 `BackupNeedsRepair = true`。 |
| **场景 3：Replace 抛异常** | `File.Replace` 抛出异常（目标被锁或磁盘满） | **排他检验磁盘前提**：<br/>若 `primary` 与 `backup` 完整且为旧版本 | **未提交 (ABORTED)** | 经磁盘验证无变动后方可裁决为 ABORTED；删除 `.tmp`；内存不安装新版本；向调用方返回 `CommitFailed`。<br/>*注：若检验发现 primary 损坏，进入 OutcomeUnknown。* |
| **场景 4：损坏文件隔离失败** | 修复坏主文件时 `File.Move(primary, corrupt)` 抛异常 | 坏 `primary` 仍存在，`backup` 有效 | **未提交 (ABORTED)** | 停止写入；删除 `.tmp`；从已验证的有效 `backup`（`*.save.prev`）执行冷恢复。 |
| **场景 5：隔离成功提升失败** | 隔离成功但 `File.Move(tmp, primary)` 抛出异常 | 无 `primary`，有 `corrupt` 与 `backup` | **未提交 (ABORTED)** | 将 `corrupt` 恢复回 `primary` 或直接从 `backup` 恢复；确保下一次恢复仍有可用副本。 |

#### 1.5.5 `OutcomeUnknown` 的分操作细粒度磁盘对账与隔离防线
当在原子替换瞬间发生未捕获的 I/O 异常、操作系统崩溃或断电导致提交结果未知时（`OutcomeUnknown`，对应 `InMemoryTableStore.cs:1391-1421`）：
1. **立即对 Live TableActor 施加隔离栅栏（Fence Actor）**：
   - 立即挂起该 Actor 的命令队列与 Tick 驱动；
   - 严禁继续基于陈旧的内存状态对外提供服务；
   - 严禁单凭陈旧内存回答客户端权威收据查询（`RECEIPT_QUERY`）。
2. **分操作细粒度的磁盘实际状态对账 (Per-Operation Adjudication Evidence)**：
   在独占租约保护下，重新读取并校验 `<roomId>.save` 与 `<roomId>.save.prev` 的物理完整性与 CRC/SHA-256：
   - **收据类写入 (`CommitAsync` Accepted / Ordinary Rejection / Forced Rejection)**：
     - 检查 `save.Receipts` 中是否存在匹配的 `ReceiptKey(AccountId, ScopeId, RequestId)` 且 `Api` 与 `PayloadSha256` 吻合；
     - 若收据已存在：**确证已提交 (COMMITTED)**！
       - 普通拒绝：即使 `CurrentState.StateVersion` 未推进，收据已持久化即代表已提交生效；
       - 强制拒绝 / Accepted：版本推进且收据已持久化，确证已提交；
     - 内存原子加载最新磁盘状态、收据与 Outbox，恢复 Actor 调度，对外报告已提交。
   - **无收据内部命令写入 (`CommitAsync(InternalCommand = true, Receipt = null)`)**：
     - 检验 `save.CurrentState.StateVersion == req.CommandVersion`、`save.CurrentState.LastEventSeq == newEvents.Last().Seq`、`save.CurrentState.StateHash == TablePayloadSha256.Compute(req.NextStatePayload)`、`save.CurrentState.TimingVersion == req.TimingVersion`，且 `save.LatestTimingPayloadSha256 == TablePayloadSha256.Compute(TableTimingCheckpointCodec.Encode(req.Timing))` 匹配 $\implies$ **COMMITTED**；
     - 确证已提交后原子安装内存并恢复对外服务。
   - **非收据类时序/控制/检查点写入 (`SaveCheckpointAsync`, `CommitControlAsync`, `AppendTimingAsync`, `CreateRoomAsync`)**：
     - `SaveCheckpointAsync`：检验 `save.CurrentState.TimingVersion == checkpoint.TimingVersion` 且 `save.CheckpointSha256 == TablePayloadSha256.Compute(candidateCheckpointBlob)`（同域比对 BaseCheckpointBlob 全字节哈希，非嵌套状态哈希）$\implies$ **COMMITTED**；
     - `CommitControlAsync`：检验 `save.CurrentState.ControlVersion == req.ControlVersion`、`save.CurrentState.TimingVersion == checkpoint.TimingVersion` 且 `save.CurrentControlSnapshotSha256 == checkpoint.ControlPayloadSha256` 匹配 $\implies$ **COMMITTED**；
     - `AppendTimingAsync`：检验 `save.CurrentState.TimingVersion == req.ExpectedTimingVersion + 1L` 且 `save.LatestTimingPayloadSha256` 匹配 $\implies$ **COMMITTED**；
     - `CreateRoomAsync`：检验主文件存在且哈希匹配初始检查点 $\implies$ **COMMITTED**。
   - **确证未提交 (Conclusively Not Committed / ABORTED)**：
     - 仅当磁盘主文件物理完整且各项版本号、收据字典与载荷哈希均处于本次请求发生前的旧代次时，方可裁决为 ABORTED；回滚内存，对外报告 `CommitFailed`。
3. **主文件损坏且备份为旧代次的未决隔离防线 (Inconclusive / Corrupt-Primary)**：
   - 若磁盘主文件 `<roomId>.save` 损坏不可读，且唯一的有效备份 `<roomId>.save.prev` 属于更早的历史代次：
   - **历史备份不存在当前请求的收据，绝不能反推“当前请求未曾提交”**（因为损坏的主文件可能已经包含了提交事实）；
   - **保持 Fenced OutcomeUnknown**：严禁自动将损坏主文件视为未提交而盲目重试命令或执行可能破坏 136 张牌守恒的副作用操作；系统保持隔离并报告 `OutcomeUnknown`，等待管理性对账或冷恢复仲裁。
4. **成功发布后不可跳过内存安装**：
   - 一旦物理文件替换原语返回成功，即使后续调用线程收到取消信号（`OperationCanceledException`），**绝不允许跳过内存安装**；
   - 若内存安装过程中发生不可恢复异常，必须强制隔离 Actor 并执行全量冷恢复后再对外提供服务。

### 3.4 生命周期状态机、取消语义与并发仲裁

#### 3.4.1 OCE-Only 取消边界与未取消故障稳定错误抛出
1. **首次打开 (`New` $\to$ `Open`)**：
   - 若 `cancellationToken.IsCancellationRequested == true`：中止初始化，释放已获取的文件排他锁，停止 Actor，删除临时文件，通道进入 `PermanentlyClosed`，向调用方抛出 **`OperationCanceledException`**；
   - 若 Token **未取消**，但因底层 I/O 故障、存档文件损坏回退失败、或文件锁冲突抛出异常：执行完全相同的资源清理（释放文件锁、停止 Actor），通道进入 `PermanentlyClosed`，向调用方抛出稳定的领域异常 **`LocalTableException(LocalTableErrorKind.Unavailable, ex.Message)`**。**严禁在未取消时隐式吞掉错误抛出 OCE**！
2. **暂态重新打开 (`TransientClosed` $\to$ `Open`)**：
   - 若 Token 取消：通道保持在 `TransientClosed`，底层 Actor 与文件锁**严格保持存活**，向调用方抛出 OCE；
   - 若 Token 未取消但打开失败：通道保持在 `TransientClosed`，底层 Actor 与文件锁保持存活，向调用方抛出 `LocalTableException(LocalTableErrorKind.Unavailable, ...)`，允许上层后续重试。

#### 3.4.2 暂态关闭取消与资源保留规则
- 调用 `CloseAsync(permanent: false)` 时：
  - 目标是断开当前会话连接，但保持后台本地服务与物理文件排他锁以备快速重连；
  - 若等待暂态关闭的调用方 Token 被取消，调用方收到 OCE，但后台仍完成会话断开并进入 `TransientClosed`；
  - **严禁因暂态关闭等待者取消而停止底层 Actor 或释放文件锁**！

#### 3.4.3 并发 Open 的独立 Waiter 令牌与全等待者取消分流
- 当多个线程/调用方并发调用 `OpenAsync` 时，共享底层的打开执行 Task；每个调用方独立监听各自的 `CancellationToken`；
- 单个 Caller Token 触发取消仅使本方 Task 抛出 OCE，不影响其他未取消的等待者；
- **全等待者取消分流机制 (All-Waiters Cancellation Branching)**：
  - **在 `New` 状态下（初次打开）**：若所有等待者均取消，底层打开 Task 被中止，回滚并释放物理文件排他锁与 Actor，通道进入 `PermanentlyClosed`；
  - **在 `TransientClosed` 状态下（暂态重新打开，含唯一等待者取消）**：若所有等待者均取消，底层重新连接 Task 中止，但**通道严格保持在 `TransientClosed`，底层 TableActor 与文件排他锁严格保持存活**，等待后续重试或显式永久关闭！

#### 3.4.4 永久关闭优先升级（Permanent Closure Wins）、取消与清理等待
1. **永久关闭原子升级**：若已有暂态关闭在进行中，随后有调用方发起 `CloseAsync(permanent: true)`，操作原子升级为永久关闭。暂态关闭逻辑完成后必须继续执行 Actor 停止与文件排他锁释放，所有永久关闭调用方方可返回。
2. **永久关闭等待者取消与后台清理继续**：
   - 若调用 `CloseAsync(permanent: true)` 的等待者 Token 发生取消，该调用方收到 OCE 退出；
   - 但**底层 Actor 停止与文件排他锁释放的清理 Task 在后台无条件继续执行直至完全释放**；
   - 任何后续到达的 `CloseAsync(permanent: true)` 调用方必须 `await` 该后台清理 Task 完成，确保返回时物理文件锁已 100% 释放。
3. **Open 与 Close 串行化仲裁与 New 状态规则**：
   - `OpenAsync` 与 `CloseAsync(permanent: false)` 严格通过门禁 `_transitionGate` 串行执行；
   - **在 `New` 状态下独立调用 `CloseAsync(permanent: false)`**：尚未建立连接，无会话需要断开，直接返回 `Task.CompletedTask`，**通道保持在 `New` 状态**，零物理资源占用，后续仍可正常发起首次 `OpenAsync`；
   - **在 `New` 状态下调用 `CloseAsync(permanent: true)`**：若当前有并发的初次 Open 正在获取锁，发出中止信号并等待其清理完毕；通道进入 `PermanentlyClosed`，零物理资源持有，返回 `Task.CompletedTask`；
   - **在 Open 进行中调用 `CloseAsync(permanent: false)`**：排队等待 Open 完成后断开会话并进入 `TransientClosed`，保持锁与 Actor 存活。

依据 `V5-P4.2-SHELL-PREPARATION.md` §5.5，本地单机运行环境严格遵守目录边界：

| 逻辑标识 | 标准路径 | 拥有者 | 读写权限约束 |

### 4.3 LOCAL 模式安全边界与资产防篡改
1. **源头标识（Origin Invariant）**：
   本地单机模式生成的所有存档头、对局收据及事件记录中，`origin` 字段被强制固定为 **`LocalSaveOrigin.Local`（`origin = LOCAL`）**。
2. **严禁越权的安全防线（Security Invariants）**：
   - **禁止伪造/上传凭证**：LOCAL 模式严禁生成、签署任何外部可上传生效的 JWT、账户票据或安全 Claims。票据发放器 `ILocalTicketIssuer` 仅在内存生成 30 秒有效期的本地占位票据，仅供满足 `TableChannelConnectRequest.Ticket != null` 的契约格式约定，严禁写盘、上报；
   - **禁止伪造/上传资产**：LOCAL 模式终局结算严禁涉及任何真实金币、出千点充值、排位段位积分变动，记录仅存在于单机战绩与本地成就归档；
   - **服务端拒绝策略**：任何带有 `origin = LOCAL` 的结算载荷，一旦尝试上传至远程服务端点（Lobby/TableService/Ranked/Wallet），远程服务端必须在鉴权层直接拒绝并记录安全告警。
3. **文档与实现状态边界**：
   在当前文档协议阶段，确认“远程服务端 LOCAL 拒绝实现校验”明确标注为 **`NOT_RUN`**（架构契约已锁定，待未来远程服务实现时贯通注入）。
