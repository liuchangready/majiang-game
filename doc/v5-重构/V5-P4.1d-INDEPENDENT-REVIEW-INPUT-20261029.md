## 2. 缺陷清单（一次给全）

### D-P41D-R1-01 — MAJOR — 已提交控制请求的同字节重放被退休 decision 错误拒绝；拒绝回执不可对账

**位置**

- `dotnet/src/Mahjong.LocalHost/LocalTableRuntime.cs:769-783`：`HandleCommandAsync` 在进入 `HandleControlCommandAsync` 的持久回执查询之前，先比较 `ExpectedDecisionId` 与当前 pending decision；不匹配时直接 `Enqueue(RejectedReceipt(...))` 并 `return`。
- `dotnet/src/Mahjong.LocalHost/LocalTableRuntime.cs:796-803`：`PrepareReceiptDigest` 在上述早退之后才执行，因此该拒绝既不写回执 digest，也不经过 actor/store 的持久回执路径。
- `dotnet/src/Mahjong.LocalHost/LocalTableRuntime.cs:1113-1155`：真正的按 `(account, scope, request)` 持久回执重放只在这里，永远到不了。
- `dotnet/src/Mahjong.LocalHost/LocalTableRuntime.cs:1476-1544`：`HandleReceiptQueryAsync` 只在 store 中找到 receipt/control record 时返回 FOUND；早退拒绝没有记录。
- `dotnet/src/Mahjong.LocalHost/LocalTableStore.cs:760-829`：`CommitControlAsync` 只在实际控制 change 提交时写入 `ControlResults`；早退路径不经过它。

**复现**

1. 同 1.3 的 ignored `probe-replay/`，构建 Release 后运行：
   ```powershell
   D:/Unity/dotnet/dotnet.exe dotnet/tests/Mahjong.LocalHost.Tests/bin/Release/net8.0/Mahjong.LocalHost.Tests.dll `
     -class Mahjong.LocalHost.Tests.ReviewProbeTests -parallelMode none -xml probe-replay.xml
   ```
2. 探针 A（重放）：打开 RawControlConnection；等待 seat0 打开真实 decision；用 `ReleaseControl(epoch=0, requestId=probe-decision-replay, decisionId=<live>)` 发送原始 wire bytes；断言首次 `Recorded`、`ControlVersion=1`；推进确定性时钟 30s，等待原 decision 退休；再次发送**完全相同的** `byte[]`（同 scope、同 request、同 bytes）；断言 `Recorded` + 原 digest + `ControlVersion=1`。
3. 探针 B（丢拒绝回执）：通过包装 channel 丢弃第一条 `ReasonCode=DECISION_MISMATCH` 的 receipt；提交一个带非当前 decision 的 `ReleaseControl`；确认 FileOutbox `PendingCommands=1`、`NeedsReconciliation=true`；重连并等待 `RECEIPT_QUERY`；断言 outbox 被解析为空。

**实际**

- 探针 A：第二次 receipt 为 **`Rejected/DECISION_MISMATCH`**，`controlVersion=1`；没有返回原 `Recorded`，也没有 `Replayed=true`。原始控制副作用确实只发生一次（版本未再步进），但动态 decision 校验覆盖了已持久化的幂等结果。
- 探针 B：重连查询完成后 **`PendingCommands=1`、`LastLookup=NotFound`**；FileOutbox 永远无法闭合。服务端确实没有第二条控制记录，但“没有记录”在这里正是缺陷：拒绝是确定性终态，却没有持久化。

**期望**

- 同 scope、同 request、同 canonical bytes 的重放，必须先于任何动态 decision/epoch/current-state 校验返回原持久结果：`Recorded`（或原状态）、原 digest、原 `EvaluatedStateVersion`、`Replayed=true`；不得产生第二次控制变更。
- 对该请求的拒绝也必须作为确定性的 request-keyed 结果持久化；丢回包后 `RECEIPT_QUERY` 应返回 `FOUND` + `Rejected` + `DECISION_MISMATCH`，FileOutbox 解析为空。
- 只有**从未记录过**的旧 decision 新请求才应被拒绝；它应与“已记录请求的重放”区分。

**证据**

- `probe-replay.xml`、`probe-replay-run.log`（SHA 见 §1.3）。
- 同缺陷已在候选分支的 post-frozen 提交 `7e03564` 中被调用方 R1 以 `ReviewerProbe_ControlReplaySurvivesDecisionRetirement` 独立复现；该提交不在冻结对象内，本报告没有使用其产物，但可作为“不是本审查环境偶发”的旁证。

**修复要求**

- 把 request-keyed 持久回执/控制记录查询提到 `ExpectedDecisionId` 新鲜度校验之前；或在早退前先做一次与 `HandleControlCommandAsync` 相同的 `(account, scope, request)` 查询，命中则返回原结果（含 `Replayed`）。
- 早退拒绝必须走与 actor 拒绝相同的持久化路径：写入 receipt digest（或等价 request-keyed outcome）和 `Rejected` receipt，再 enqueue；不能让 `Enqueue(RejectedReceipt(...))` 成为唯一动作。
- 控制 scope 的 `ValidateControlScopeAsync`（过期/撤销/角色/账户/房间）应位于任何会产生回执的分支之前，或与回执查询一起组成明确的“先持久幂等、再授权、再新鲜度”的顺序；至少不能让过期/撤销 scope 以 `DECISION_MISMATCH` 作为最终答复。
- 保留真正新请求的旧 decision 拒绝和零副作用；不得为了重放而放宽 `DECISION_MISMATCH`。

**验收断言**

- 已记录请求的 exact-byte replay（decision 已退休）→ `ReceiptStatus.Recorded`、`Replayed=true`、digest/Evaluated 与原值逐字符相等、`ControlVersion` 不再增加。
- 丢弃该拒绝回执后重连 → `ReceiptLookupStatus.Found`、`OutboxDisposition.Rejected`、`ReasonCode=DECISION_MISMATCH`、`PendingCommands` 为空、`LoadUnresolvedAsync` 为空。
- 未记录的新请求 + 真旧 decision → `Rejected/DECISION_MISMATCH`、无 `LocalControlRecord`、`ControlVersion` 不变。
- 过期/撤销 scope → `Rejected/REQUEST_SCOPE_EXPIRED`、无记录、版本不变。
- 负例矩阵至少覆盖：同 bytes/同 request、异 bytes/同 request、异 kind/同 request、同 bytes/不同 scope、丢回包/冷重启、并发 Claim/Release。
