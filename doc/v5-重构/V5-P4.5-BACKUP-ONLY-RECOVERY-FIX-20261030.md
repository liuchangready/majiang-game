## 原始失败与根因

调用方在真实 Windows Player 中把上述 baseline 复制为 `local/local-main.save.prev`，删除主文件后启动，首个真实快照竟是 `stateVersion=0`；原 3 条回执全部未恢复，物理布局重新生成，而烟测仍 native 0。该结果保留在调用方证据 `backup-only-confirmation/generated-observation.json`，不得重标为 PASS。

源码根因在 `dotnet/src/Mahjong.LocalHost/LocalTableStore.cs:180` 的 `LoadEnvelopeWithRecovery()`：`TryLoad` 对“文件不存在”返回 `null` 且 `error=null`；有效备份也返回 `error=null`。旧逻辑只检查 `primaryError == null && backupError == null` 就返回 `null`，把“主文件缺失、备份有效”误判为“没有任何存档”，上层据此创建新局；后续发布备份的分支根本不会执行。

## 修复

### 1. 恢复分类（生产代码，唯一生产修改）

`LocalTableStore.LoadEnvelopeWithRecovery()` 现在先显式记录主文件/备份是否存在，再按四类处理：

1. **两者都不存在**：返回 `null`，允许房间首次开局；
2. **主文件有效**：优先返回主文件，不因备份坏而降级；
3. **主文件缺失/损坏、备份有效**：采用已验证的备份，并复用既有“临时文件 + 同卷原子 rename + 校验后发布”流程恢复 primary；发布失败抛 `Unavailable`，保留原 primary（若已隔离则恢复）和已验证备份；
4. **没有可用副本**：抛 `CorruptState`，明确拒绝，不能静默开新局。

未改变 envelope/checksum、ruleset/room 校验、物理/日志回放校验；未改验证器或 manifest；没有用 catch 吞错或测试通道强写成功。

### 2. 新回归

新增 `dotnet/tests/Mahjong.LocalHost.Tests/LocalSaveBackupRecoveryTests.cs`，7 个 Fact：

| 用例 | 断言要点 |
|---|---|
| 主缺失 + 备份有效 | 发布 primary；版本、roundId、全部 receipt 身份/字段/digest、StateHash、command/event journal 一致；恢复后的 runtime 必须 136/0 未分配且逐张位置相同；再删 primary 后由独立冷进程复验 |
| 主缺失 + 备份坏 | `CorruptState`；不创建新 primary；坏备份字节不变 |
| 两者缺失 | 允许首次开局；创建后版本 0、136 张守恒 |
| 主有效 + 备份坏 | 使用 primary，不回滚；完整 receipt 集与 136 身份不变 |
| 主坏 + 备份有效 | 采用备份、重新发布 primary、清理 `.corrupt.*`；完整身份不变 |
| 备份发布失败（主缺失） | `Unavailable`；不伪造 primary；备份仍可用，重试恢复成功 |
| 备份发布失败（主坏） | 隔离的坏 primary 被恢复原字节；备份仍可用，重试恢复成功 |

测试不是只比较“文件存在”。恢复版本/状态 hash/roundId/原 receipt 集合（account/scope/request、status、evaluated/command/event、reason、canonical digest、durable payload digest、created/expires）和 136 张逐张位置均由真实保存文件与 `LocalTableRuntime` 读取比对。单局 roundId 仍可能是 `local-main-r1`，因此断言使用保存文件中的实际 roundId，并同时比较物理摘要、状态 hash 和回执集合，不把 roundId 文本当成是否重开的证据。

### 3. 独立冷进程读模式

在既有 `Mahjong.LocalHost.CrashWorker` 增加独立 `backup-recovery-read` 模式，不改旧模式语义。该模式单独进程打开真实 `LocalTableRuntime` 恢复路径，输出版本、事件序号、状态 hash、roundId、136 hash/数量、完整 receipt 集 digest、primary/backup 存在性与 SHA；不提交动作、不推进游戏、不回写权威状态。测试中的冷进程用例和真实 Player 数据的冷读都使用它。
