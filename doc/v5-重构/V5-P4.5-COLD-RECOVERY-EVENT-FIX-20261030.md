## 3. 根因裁决

### 3.1 不是权威提交失败

- 回执 `Applied`，`evaluatedVersion=4`、`commandVersion=5`、`eventSeq=10` 合法。
- 存档版本从 3 推进到 5；旧 3 条回执保留，前后 136 张守恒。
- 故原 31 不能重标为“权威未提交”或“用户 UI 丢事件”；同样也不能仅凭 `Applied` 推断 UI 事件正确。

### 3.2 已实测的烟测观测缺陷（验证逻辑）

旧 `RunLocalHostSmokeSequence` 在提交后轮询 `SessionCoordinator.Current`，要求“当前 stateVersion 大于提交前 + 当前 batch 为 Incremental + 当前 batch 事件数 > 0”。`Current` 只保留**最新**一次发布，等价的空增量/决策刷新会覆盖动作批次。

最终真实 Player 与 PlayMode 都抓到了同一形态：

```text
accept=2  Incremental  stateVersion=1  eventSeq=2  events=[TileDiscarded#1.0@cmd1/seat0]   ← 动作批次
accept=3  Incremental  stateVersion=1  eventSeq=2  events=[]                                ← 同状态空刷新
accept=4  Incremental  stateVersion=2  eventSeq=4  events=[TileDiscarded#3.0@cmd2/seat1]
```

旧代码若在 accept=3 之后采样 `Current`，会得到“stateVersion=1、Incremental、0 事件”，即使 accept=2 已经确认。这是**观测逻辑的丢失**，不是 Client 丢事件；批次已经由 `SessionCoordinator.Changed` 在主线程发布，独立 observer 能保留它。

同时，旧逻辑对“合法空批次”一律按失败处理：不检查 Applied 回执、不检查 action kind、不把 receipt 的 `command_version` 与事件的 `command_version` 关联，也没有在响应窗口没有 Discard 候选时继续推进。

### 3.3 已实测的产品缺口（范围外，未修改）

原 31 的直接可判定原因不是“瞬时覆盖”，而是 **Pon/Chi 域事件没有协议可见事件映射**：

- `dotnet/src/Mahjong.TableRuntime/TableEventProjection.cs` 的 `FromRoundEvent` 显式映射了 `TileDiscarded`、`TileDrawn`、`KanDeclared` 等，但没有 `RoundEventType.PonDeclared` / `RoundEventType.ChiDeclared` 分支。
- 只读探针（当前源码、无宿主）实际输出：

```text
TileDiscarded     => TileDiscarded
PonDeclared       => NULL_NO_PROTOCOL_EVENT
ChiDeclared       => NULL_NO_PROTOCOL_EVENT
ResponseClaimed   => NULL_NO_PROTOCOL_EVENT
ResponseWindowOpened => NULL_NO_PROTOCOL_EVENT
```

探针日志：`logs/projection-probe.log`，SHA256 `7F4913624DF7D7F1085804C97B6D4AA5480420586A200800CE3868581FE60C3C`。

- 可见性矩阵 `V5-0-VISIBILITY-MATRIX.md:56` 把 `PonDeclared` 列为公开事件；实现与矩阵不一致。
- 因此原 31 中“动作已 Applied、eventSeq 已到 10、但 batch 为空”是**合法空增量**；不是 Client/协调器丢了已投影事件。旧烟测要求这个动作必须出现可见事件，因而退 31。

**根因裁决：**

1. **原 31 的直接原因：** 产品事件投影缺口（Pon/Chi 无协议事件）+ 旧烟测把“已 Applied 的 Pon/Chi 空批次”当失败。
2. **独立验证逻辑缺陷：** `Current` 轮询会丢失真实动作批次（已由真实 Player/PlayMode 证明）；旧逻辑也没有 receipt/command_version/action kind 关联。
3. **不是：** 权威未提交、存档回执丢失、`SessionCoordinator`/`Client` 丢弃已投影事件、UI 事件正确性已证明。

## 4. 最小修复

### 4.1 新增独立 observer

`ConfirmedVisibleEventObserver`（纯 C#，不引用 Unity 类型）：

- 在动作提交**之前**订阅 `ISessionView.Changed`，保存每次已接受发布的不变副本；不再从最新 `Current` 读瞬时值。
- 只接受满足以下全部条件的确认：
  - `batch.Kind == Incremental`；
  - session/room/table/role/seat/scope/binding/connection/owner 与提交前 baseline 完全一致；
  - round 与 baseline 一致；
  - `batch.StateVersion > baselineStateVersion`；
  - 回执为 `OutboxDisposition.Applied` / `ReceiptStatus.Applied`；
  - 事件的 `CommandVersion` **等于**回执的 `CommandVersion`（真实 contract 字段，不捏造 correlation 字段）。
- Baseline 不作为动作事件；旧 binding/epoch/round、无关 AI 命令、重复帧、仅 stateVersion 增大、仅 Sent/Applied 均不能确认。
- `FindActionPublication(commandVersion)` 用“stateVersion == 回执 command_version 的第一条 incremental 发布”区分：
  - 该发布不存在：动作已 Applied 但发布未被观测到 → 失败；
  - 该发布存在且事件数为 0：合法空批次/state-only；
  - 该发布存在且有事件，但没有匹配回执 command_version 的事件：关联异常 → 失败。
- `Dispose` 正常退订；不缓存 ticket/token，不读取存档，不修改 snapshot。

### 4.2 烟测推进

`GameBootstrapper.RunLocalHostSmokeSequence`：

- 提交前构造 observer 并订阅 `ReceiptResolved`，`finally` 退订/释放。
- 最多 3 次真实 Client 动作：
  - 优先 `DiscardTile`；没有 Discard 候选时使用当前合法候选（例如响应窗口 Pon/Pass）。
  - 每次动作都以真实 `TableCommandIntentFactory` 构造并 `SubmitAsync`，不绕过 Client/协调器。
  - 用 observer 的 receipt+event 关联判定成功；不读 `Current` 瞬时 batch 作为成功条件。
  - 已 Applied 且动作发布为空：
    - 非 Discard：记录 `SMOKE_STEP:LOCAL_ACTION_STATE_ONLY`，继续下一个真实决策；
    - Discard：仍失败（Discard 必须产生可见事件）。
  - 已 Applied 但动作发布从未被接受：失败（缺失发布，不当 state-only）。
- 不修改 snapshot/phase/authority，不修改 `SessionCoordinator`/`Client`，不强行给 Pon 造动画。
- 没有用固定 2 秒“等一等”作为 state-only 判据；判定完全由回执 `command_version` 与该版本的已接受发布驱动。
