## 1. 交付摘要

实现了本座位“托管给电脑 → 权威回执/新快照 → 显式收回控制权”的真实 UI 与 V2 命令链路：

- 复用 `CommandPayloadFactory.ClaimControl/ReleaseControl` 的既有 canonical tag 20/21，不恢复旧 tag 1 冲突字段，不新增控制 API。

- 真实 LocalHost + Client PlayMode 用例及真实 Windows Player opt-in probe 均完成一次 `release → reconnect → claim`，权威代次 `0 → 1 → 2`，旧 epoch 动作被 `STALE_CONTROL_EPOCH` 拒绝。

## 3. 控制状态投影

### 3.1 Contracts/Wire

`Mahjong.Contracts.PlayerControlView`：

- `ControlEpoch`（合法 epoch 0 与“无资料”由 nullable 区分）
- `ControlledByComputer`（Domain 的 Computer/Takeover 映射为 true；LocalHuman/RemoteHuman 为 false）
- `ControlVersion`（独立控制事件序列）

`PrivatePlayerView.Control` 为 nullable。Wire 新增：

```proto
message PlayerControlView {
  uint64 control_epoch = 1;
  bool controlled_by_computer = 2;
  uint64 control_version = 3;
  reserved 4 to 8;
}
```

`PlayerPrivateView.control = 18` 使用未占用、未 reserved 的 tag；既有 `reserved 9 to 15` 未改变。`PublicSnapshot/PublicMatchView/PublicBoardView` 不增加任何控制字段。

`ProjectionWireMapper` 只在 `source.Control != null` 时写入 Wire；null 保持“unknown”，不会被写成 epoch 0。

### 3.2 TableRuntime

`TableSeatControlProjection` 由 `TableActor` 在 `CaptureStreamProjection()` 中与快照数据一起捕获：

- `_control.Capture()` 与 `_controlVersion` 来自同一 actor turn。
- seat 投影校验 `control.Seat == seat`，跨席控制事实直接 `TableProjectionException(InvalidContext)`。
- `BuildStreamFrame` 校验捕获的 control version 等于当前安装版本、捕获 epoch 等于当前安装 epoch；不一致 fail-closed，不补新代次。
- 公开流不接收控制投影；只有 seat 私有点携带。
- `TableProjectionContractMapper.MapPlayerSnapshot` 原样保留 `source.Private.Control`。

### 3.3 托管后的流语义

已接受宿主在 control epoch 变化时仍会按既有 `StaleControlEpoch` 规则关闭旧 seat private stream（`TableStreamActorTests/TableStreamWireIntegrationTests` 既有断言未改）。因此本轮没有放宽/改写该安全规则，而是让 UI 在回执后保持“等待牌桌确认”，并由真实产品路径 `返回菜单 → 重新进入本地牌桌` 取得新基线。重连后控制者保持自动化，**不会自动收回**；必须再显式点击“收回控制权”。

这一限制已在 UI 状态文案中明确提示“如未更新请重新进入牌桌”，但没有展示协议字段/tag。

## 4. UI 行为

- `TableCommandIntentFactory.CreateReleaseControl/CreateClaimControl`：
  - 只接受本座位私有点；
  - `roundId` 来自确认 view；
  - `expectedControlEpoch` 来自确认控制状态；
  - `requestId/scopeId/stateVersion/ownerEpoch` 来自现有 owner 上下文；
  - 控制命令允许自动/人工转换检查，不允许反向重复；
  - 无控制状态时返回 `CONTROL_STATE_UNAVAILABLE`，不猜 epoch 0。
- 普通动作/绝技命令在自动化控制、无控制投影时 fail-closed（`CONTROL_AUTOMATED`/`CONTROL_STATE_UNAVAILABLE`），必须显式收回。
- `TableInteractionState`：
  - 控制状态变化会清除旧选择与旧 pending；
  - 重复点击同一控制意图只保留一个 pending/requestId；
  - 控制回执 `Applied/Recorded` 后 pending 保留，等待确认快照，不用回执乐观宣称收回成功；
  - `Unknown` 保持 `NeedsReconciliation`，不自动重做。
- `TablePresenter.RenderControl`：
  - 观战/非授权：隐藏按钮，只读提示；
  - 无控制投影：两个按钮可见但禁用并给出原因；
  - Ready + 人工：显示/启用“托管给电脑”，隐藏/禁用“收回控制权”；
  - Ready + 自动：显示/启用“收回控制权”，隐藏/禁用“托管给电脑”；
  - 发送中/未知/非 Ready/暂停/结束：禁用并给出稳定中文原因；
  - UI 不显示协议字段、tag、epoch 数字。
- 动作/绝技面板在自动化、无控制投影或控制 pending 时隐藏，防止 UI 在电脑控制期间继续提交旧决策。

### 7.1 第 2 轮独立审查返修：跨席 ControlVersion 与提交状态

审查确认的缺陷：`SameControlAuthority` 把全桌 `ControlVersion` 纳入本座位控制权比较。其他座位的控制变化会推进该版本，导致本座位仍在发送或结果未知的 Release/Claim 被清除，UI 重新启用并可创建第二个 requestId；未决普通动作也可能被丢失。

修复：

- `SameControlAuthority` 只比较本座位 `ControlEpoch`、`ControlledByComputer` 与 presence；`ControlVersion` 不再解除本座位 pending 保护。
- 本座位 epoch/controller 真实变化仍清除 pending；`OnBaselineReset`/合法重连仍清除 pending 并允许新请求。
- `SubmitIntentAsync`：
  - sink 为 null/`CanSubmit=false`、`_latestView` 缺失、sink generation 不匹配 → 未发送，`AbandonUnsent` 清理 pending，允许用户重试；
  - 参数/Client 前置条件异常（`ArgumentException`/`InvalidOperationException`，发生在持久化/发送之前）→ 未发送，清理 pending；
  - 超时/取消/通道异常等可能已持久化或部分发送的异常 → `MarkDeliveryUnknown`，保留原 requestId、标记 `NeedsReconciliation`，不自动重做；
  - Client 返回 `Sent=false` 且 `NeedsReconciliation/DeliveryUnknown`，或 `LastReceipt=Unknown` → 同样标记未知；
  - 提交期间会话绑定变化但 pending 仍是原请求 → 标记未知，不分配新请求。
- 新增回归：
  - TableModel：跨席 ControlVersion 变化不清理发送中控制请求、不清理 Unknown 控制请求、不丢失普通动作 pending；本座位真实变化清理并允许 Claim；baseline 重连清理并允许新 requestId。
  - PlayMode：真实 baseline 上使用 fake sink 验证 sink 不可用/ generation 不匹配均清理 pending 且 0 次调用；取消异常标记 Unknown、按钮保持禁用、二次点击不产生第二次调用或新 requestId。
- 第 2 轮实际结果：TableModel **160/160**、Contracts **152/152**、TableRuntime **458/458**、EditMode **6/6**、PlayMode **2/2**、Player r7 build/probe exit **0**。
- 第 2 轮首败保留：PlayMode 编译首败 `ISessionView` 缺少 `Mahjong.Unity.UI.Session` using；随后 fake sink 的预期异常用 `Debug.LogError` 被 Test Framework 判为 unhandled log；改为 `LogWarning` 后通过。日志分别保留为 `unity-playmode-control-round2.log`、`unity-playmode-control-round2b.log`。另一次 `TableVisibleEventBatch` 缺失是生成插件已恢复旧版导致，重新 build-shared 后通过，日志为 `unity-playmode-control-round2d.log`。

### 7.2 第 3 轮独立审查返修：optional Control 存在→缺失→恢复

审查确认的缺陷：`ApplyConfirmedView` 以 `_hadControlState && !SameControlAuthority(_view?.Control, view.Control)` 判断本座位控制权变化；当同一绑定、更新版本的快照缺失 optional `Control` 时，会把“缺资料”误判为权威变化并清除 pending。随后投影恢复原 epoch/controller 时 `_hadControlState` 已为 false，按钮重新启用，可产生第二个 requestId。

修复：

- `TableInteractionState` 新增“最后可信本座位控制权威”记忆：`_hasKnownControlAuthority`、`_knownControlEpoch`、`_knownControlledByComputer`。
- 只有**新快照携带 control 且 epoch/controller 与该记忆不同**时才判定权威变化并清除 pending。
- control 缺失不清除 pending，也不抹掉已知权威；普通动作 pending 同样保留。
- control 缺失→恢复同 epoch/controller：pending 原样保留，重复点击仍为 `ALREADY_PENDING`，不会产生第二个 requestId。
- control 缺失→恢复不同 epoch/controller：判定真实权威变化，清除 pending 并允许新 Claim。
- `OnBaselineReset`/`OnIdentityChanged` 仍是显式生命周期规则：清除 pending 并重置已知权威；`BaselineReconnectClearsPendingAndAllowsFreshRequest` 继续验证合法重连可收敛。
- 新增回归：发送中/Unknown 的 control 存在→缺失→同 epoch/controller 恢复、普通动作同路径、缺失后真实变化；TableModel 最终 **164/164**。
