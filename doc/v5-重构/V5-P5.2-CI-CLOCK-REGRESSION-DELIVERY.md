## 3. 可证伪根因

### 3.1 根因：fixture 混用“注入时钟”和“真实墙钟”

旧 fixture 的事实链：

1. `P52TestSupport.ManualTableClock`：
   - `UtcBase` 在对象构造时取一次真实 UTC；
   - `Now = 1000L`；
   - `UtcNowMs = UtcBase + Now`，因此在 fixture 生命周期内 **冻结在构造后约 1 秒**。
2. `P52Fixture.CreateAsync()`（旧）用 `DateTimeOffset.UtcNow` 创建初始 checkpoint 时间。
3. `P52Fixture.BuildCommit()`（旧）用 `DateTimeOffset.UtcNow` 写 receipt `created/expires` 与 `TableTimingCheckpoint.CapturedAtUtcMs`。
4. 失败的 R1 用例（旧）在 `PostgresR1RegressionTests.cs:360` 用 `DateTimeOffset.UtcNow` 创建 checkpoint 时间。
5. 该用例恢复时 `RecoverAsync` 使用 boot `r1-recovery-boot`，而持久 timing 的 boot 是 `p52-boot-1`，因此进入 `TableRecoveryService` 的 **跨 boot** 分支：

```text
dotnet/src/Mahjong.TableRuntime/TableRecoveryService.cs:1211  sameBoot = false
TableRecoveryService.cs:1228  if (timingCapturedUtc > 0 && nowUtc < timingCapturedUtc)
TableRecoveryService.cs:1230      return Failed(ClockRegression, "UTC time moved backwards across boot.");
```

6. `nowUtc` 来自 `_clock.UtcNowMs`，即“fixture 构造时刻 + 1 秒”；`timingCapturedUtc` 来自真实墙钟写入，发生在用例更晚的位置。只要 **fixture 创建到 durable timing 写入之间的真实耗时超过 1 秒**，就必然满足 `nowUtc < timingCapturedUtc`，恢复被正确守卫拒绝，测试假失败。

这不是产品 UTC 回退：

- 系统墙钟没有回拨；是 **两个不同时间基准** 在做跨 boot 比较；
- 持久化值本身是正确、较晚的真实 UTC，DB 中没有时间倒序；
- 失败发生在 `TableRecoveryService` 的跨 boot UTC 比较处，早于最终 lease 复核；
- `table_lease`、`request_scope` 使用 PostgreSQL `clock_timestamp()`，不是本次被拒绝的比较来源。

也不是“持久化顺序或精度”问题：

- 失败用例的 commit 已成功，事件/receipt/state 已提交；
- XML 只有 `CLOCK_REGRESSION`，没有 event gap、ordinal、receipt 或 hash 错误；
- 时间以整数毫秒持久化，原始 XML 与失败消息均能读到完整值；
- 失败是“拿真实写入时间与冻结的 1 秒后时钟比较”，不是失序或截断。

### 3.2 为什么同 SHA 的 push run 会过

旧 fixture 的通过条件不是“产品正确”，而是该用例从 fixture 创建到 durable timing 写入 **恰好小于 1 秒**：

| 运行 | 该用例耗时 | 结果 |
|---|---:|---|
| PR 40593411699 | 5.861 s | FAIL `CLOCK_REGRESSION` |
| push 40593403558 | 0.983 s | PASS |
| 本树未修改 HEAD 基线 | 1.729 s | PASS（关键写入段仍 <1 s） |

因此不能以一次绿色证明 fixture 正确；也不能把失败归为不可解释的随机 flaky。它是确定性的测试缺陷，触发量是真实墙钟延迟。

### 3.3 负例预测（已实跑验证）

预测：把 fixture 的注入 UTC 原点向后移动 10 秒（不 sleep，确定性地模拟“创建后已过 10 秒”），旧 fixture 必然在跨 boot 恢复时报 `CLOCK_REGRESSION`；修复后同一测试通过。

实际（旧 fixture + 新回归测试）：

```text
CLOCK_REGRESSION: UTC time moved backwards across boot.;
persistedTimingUtc=1793142073171;
recoveryClockUtc=1793142063815;
wallUtc=1793142073670
```

`persistedTimingUtc - recoveryClockUtc = 9356 ms`，正是 10 秒位移减去 fixture 的 1 秒初始偏移。该值直接证明“持久 timing 用墙钟、恢复用冻结时钟”，而不是墙钟回退。

## 4. 修复（最小、确定性）

### 4.1 生产守卫保持原样

没有修改 `TableRecoveryService`、`TableActor`、Infrastructure、迁移或 CI 脚本。跨 boot UTC 倒退必须继续 fail closed；本任务不删除 `NonEmptyCheatLedgerAndFacts_WithCheckpointAndTail_RecoverStrictly`，不放宽 `CLOCK_REGRESSION`，不增加 catch/retry/固定 sleep/容差。

### 4.2 单一时钟源映射

| 文件 | 旧行为 | 新行为 |
|---|---|---|
| `P52TestSupport.cs` `CreateAsync` | 初始 checkpoint UTC 取真实墙钟 | 取 `clock.UtcNowMs` |
| `P52TestSupport.cs` `BuildCommit` | receipt 时间与 timing `CapturedAtUtcMs` 取真实墙钟 | 取 `Clock.UtcNowMs` |
| `P52TestSupport.cs` `BuildRejectedCommit` | receipt 时间取真实墙钟 | 取 `Clock.UtcNowMs` |
| `PostgresR1RegressionTests.cs` 失败用例 | `checkpointUtc` 取真实墙钟 | 取 `fixture.Clock.UtcNowMs` |
| `P52TestSupport.cs` `CreateAsync` scope | 默认 scope 时间取真实墙钟 | **保持真实墙钟**（见 4.3） |

原则：**durable recovery timing/receipt 使用注入时钟；scope 生命周期使用数据库/墙钟时间。** 两者不混用。

### 4.3 为什么 scope 不跟随注入时钟（一次中间失败）

首次修复曾把默认 scope `issuedUtcMs` 也改为 `clock.UtcNowMs`。旧 fixture 的时钟在构造后 +1 秒，导致 scope 的 `issued_at` 比真实墙钟略晚；随后测试用真实墙钟撤销/过期，触发：

```text
Npgsql.PostgresException 23514:
new row for relation "request_scope" violates check constraint "ck_scope_time"
```

以及显式 `expires=now+700ms` 时 `Scope expiry must follow issue time`。该中间运行（固定2 之前）为：

```text
fixed1: Total=37, Passed=34, Failed=3, Errors=0, Skipped=0, Not Run=0
```

3 项失败均为 `PostgresTableStoreTests` 的 scope 生命周期测试。修正为“scope 继续使用真实墙钟、只把 durable recovery 时间统一到注入时钟”后，37/37 通过。该中间失败与证据保留在 `build/.../fixed1-20261028-070233/`，不冒充最终结果。

### 4.4 新增定向反证

在 `PostgresR1RegressionTests.cs` 增加 2 项：

1. `CrossBootRecovery_UsesInjectedUtcTimeline_NotWallClockElapsed`
   - 在 fixture 创建后把 `Clock.UtcBase` 后移 10 秒（无 sleep）；
   - 提交一个真实 durable command；
   - 断言恢复成功；
   - 断言持久 timing 的 `CapturedAtUtcMs` 等于注入时钟 `UtcNowMs`。
   - **旧 fixture 稳定失败**（见 §3.3），修复后通过。
2. `CrossBootRecovery_RejectsGenuineUtcRollback_WithInjectedClock`
   - 同一注入时钟在 commit 后严格向后移动 5 秒；
   - 断言 `Failed`、`TableRuntimeReasonCode.ClockRegression`，且 detail 含 `UTC time moved backwards across boot.`；
   - 证明修复没有放宽真实跨 boot 倒退。
