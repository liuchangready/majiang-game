### 1.2 第 1 轮独立复验失败与修复

Codex 在 HEAD `0298a1e` 执行：

```powershell

# Exit 1: Total 53 / Passed 51 / Failed 1 / Skipped 1
```

失败：`WebSocketTableChannelGuardTests.SendAdmissionIsBoundedAndTimesOutWithSlowConsumer`，`WebSocketTableChannelGuardTests.cs:70`，Expected `SLOW_CONSUMER`，Actual `STALE_CONNECTION`。

根因与修复：

1. **发送原因竞态**：首个 sender 的 `SendTimeout` 与排队 sender 的准入等待同时到期。首个 sender retire 连接后释放 slot，排队 sender 的 `SemaphoreSlim.WaitAsync` 可能先成功、随后在写锁前看到 `IsCurrent == false`，旧代码无条件报 `STALE_CONNECTION`；即使准入等待先超时，也可能被另一 sender 的 retire 覆盖原因。现在每个 `Connection` 记录**首次 retire 的 code/permanent**；`FailSend`/`ClosedFor` 区分：
   - 同一连接已 retire 且未被替换 → 返回该连接自身的 retire 原因（`SLOW_CONSUMER` / `LOCAL_CLOSED` / `TRANSPORT_LOST` 等）；
   - 已被新的 `OpenAsync` 替换 → `STALE_CONNECTION`。
   因此同连接退避超时不再被误报为旧连接。新增确定性覆盖：双方 `SLOW_CONSUMER`、显式关闭双方 `LOCAL_CLOSED`、重开后旧 sender `STALE_CONNECTION` 且新连接可发送。
2. **payload 复制早于准入**：`SendAsync` 原先在等待 `SendSlots` 之前执行 `wireEnvelope.ToArray()`，大量并发调用会各自持有大消息副本，`MaxPendingSends` 无法约束。现在先取有界 slot，再复制；超时/取消/释放路径仍通过 finally 递减在途计数。新增内部诊断计数和 20 并发、2 slot 的测试，断言准入复制数 ≤ 2、在途复制归零。
3. **握手 deadline 被逐次 Pump 重置**：`HandshakeTimeout` 原先每次 `PumpOnceAsync` 重新 `CancelAfter`，持续非 baseline 消息可无限延长。现在每次连接尝试建立**绝对单调 deadline**（`Open` 前锚定），`OpenAsync` 与每次 pump 都只用剩余时间，只有 Ready 才清除；WELCOME 后的连续非 baseline 消息不能延长期限。新增手动单调时钟测试：每收一条消息推进 100 ms、真实耗时 60 ms，握手 250 ms，断言最多收到 5 条即超时。

`ITableChannel` 仍只搬运不透明 Wire envelope。新实现的分工是：

## 2. 实现摘要

### 2.1 `WebSocketTableChannel`

- **消息边界**：一个完整 binary WebSocket message 对应一个 envelope。`ReceiveAsync` 循环读取 fragment，直到 `EndOfMessage`；以累积字节长度判断上限，超限立即失败，绝不返回部分 envelope。
- **明确拒绝**：
  - 空 binary → `MALFORMED_MESSAGE`（permanent）
  - 文本帧 → `PROTOCOL_VIOLATION`（permanent）
  - 超过 `MaxMessageBytes` → `MESSAGE_TOO_LARGE`（permanent）
  - 分片中途断开 → `TRUNCATED_MESSAGE`（transient，交由会话重连+对账）
  - 服务端 Close frame → 映射到既有 `ProtocolErrorCode`/关闭码
  - 单个消息接收超时 → `RECEIVE_TIMEOUT`（transient）
- **有界收发**：
  - 接收只允许一个 `ReceiveAsync` owner/connection；并发第二个调用是编程错误。
  - 接收不建立无界后台队列；同一时刻最多累积一条消息，上限默认 `WireLimits.MaxInboundMessageBytes`（1 MiB），慢读由 `ReceiveMessageTimeout` 明确断开。
  - 发送使用 `MaxPendingSends` 的有界准入 + 单写锁；队列满时调用方等待，超时返回 `SLOW_CONSUMER`，不会无限堆积。payload 复制在取得 slot 之后发生，未准入的调用不持有大消息副本。
- **retire 原因**：同一连接被超时/显式关闭/传输失败 retire 后，排队的 sender 得到该连接的实际原因；只有被新的 `OpenAsync` 替换的旧连接才返回 `STALE_CONNECTION`，不再把同连接并发失败误报为旧 binding。
- **旧连接隔离**：每次 `OpenAsync` 创建新 generation；旧 socket 被 abort/dispose，旧接收任务返回字节后再次校验 current connection，失败即 `STALE_CONNECTION`，不会投递到新 binding。
- **TLS/URL**：
  - 生产默认只接受 `wss://`；`ws://` 仅在 `AllowInsecureLocalWebSocket` 显式开启且 `Uri.IsLoopback` 时接受。
  - 拒绝 URL userinfo、query、fragment，避免票据进 URL。
  - 未提供关闭证书校验的开关；`wss` 使用 `ClientWebSocket` 默认证书验证。
- **票据**：`TableChannelConnectRequest.Ticket` 只用于校验非空；本通道不把它放入 URL、header、日志或磁盘。HELLO 仍由既有 `TableSession` 生成。

### 2.2 `HeartbeatTableChannel`

- 使用既有 `WireCodec.Decode` 校验 16 位小写十六进制 nonce；非法 nonce/非 PING/PONG/空 beat 均拒绝。
- 收到合法 PING 时按同一 binding 回显精确 nonce 的 PONG；PONG 必须匹配某个 outstanding client PING，否则 `PROTOCOL_VIOLATION`。
- 从 WELCOME `ServerLimits` 协商 `heartbeat_interval_ms` / `idle_dead_ms`；无值或非法值有默认下限；到期未收到任何入站帧则 `HEARTBEAT_TIMEOUT`。
- 心跳在 WELCOME 前一律拒绝；WELCOME 后要求 `session_id`、`room_id`、`seat_id`、`binding_epoch` 与会话绑定完全一致；重复/更旧 binding 的 WELCOME 不会把控制层切回旧 binding。
- 心跳 PONG/PING 的收发不进入 `TableSession` 的业务分支；业务 envelope 原样透传。

### 2.3 `TableSessionRunner`

- 只调用既有 `IGameSession.OpenAsync` / `PumpOnceAsync`；不直接操作 channel、outbox 或 receipt。
- 每次连接尝试都调用 `ITableTicketProvider.GetTicketAsync`，传入 attempt、resume session id、上次失败码；不缓存、不复用旧票据。
- 指数退避：`InitialBackoff × BackoffMultiplier^n`，`MaxBackoff` 封顶；`MaxReconnectAttempts` 可配置，0 表示首次失败即停。
- 每次连接尝试在 `OpenAsync` 前锚定一个绝对的单调 `HandshakeTimeout` deadline；`OpenAsync` 与每次 pump 都只用剩余时间，只有 Ready（完整基线）才清除。持续非 baseline 消息不会重置 deadline。
- 传输永久错误、非可重试 ticket 错误立即停止；临时错误按预算重试。
- 断线后不重发业务：未决命令保持原 `requestId`/scope/字节约；重连后由既有 `TableSession` 先应用基线、再发 `RECEIPT_QUERY`。runner 和 channel 都不调用 `RetryPendingAsync` / 不生成新 requestId。
- `SnapshotChanged` / `ReceiptResolved` 仍在调用线程同步触发；Unity 主线程 marshalling 留给平台层。

### 2.4 测试用可控性

- `ITableClientClock` + 手动时钟测试心跳 interval/idle/nonce 与超时。
- 内部 `IWebSocketConnectionFactory` seam + fake socket 覆盖连接超时、TLS 失败映射、接收超时、发送背压、并发接收、retire 后旧字节、Dispose、调用方取消。
- 独立的最小本机 RFC 6455 `LocalWebSocketServer` 覆盖真实 loopback ws：分片、连续消息、空/文本/超限/截断/关闭、慢读、并发发送、重开、心跳、runner 重连。
- WSS 负向测试使用运行时自签名证书，验证默认证书验证仍然生效。正向信任链因本机没有受信任测试根而未运行（见 §5）。

## 5. 缺口与风险（必须保留）

1. **真实服务未接入**：没有真实 TableService、PostgreSQL、LobbyService、票据签发/轮换服务。测试使用本机最小 RFC6455 端点和 scripted channel；不能据此宣称真实 WELCOME/票据/租约/回执链路通过。
2. **正向 WSS 信任链 NOT_RUN**：共享库目标为 netstandard2.1，`ClientWebSocketOptions` 在该表面没有每连接证书回调；使用自建 CA 需要改机器证书库，未执行。负向自签名拒绝测试证明默认校验仍开启；未为了让正向测试通过而关闭校验。
3. **真实网络/代理/SNI/证书轮换未验证**：未测试企业代理、TLS 1.2/1.3 组合、证书轮换、跨物理网络、弱网、NAT 重绑定。
4. **移动端/AOT 未验证**：`ClientWebSocket` 在 Unity IL2CPP / Android / iOS 上的可用性、TLS、后台/锁屏/切网未测；本机没有 Android NDK/IL2CPP/iOS 工具链与设备。共享库虽为 netstandard2.1/C#9，但实际 Unity 裁剪/链接器保留项未验证。
5. **主线程投递未实现**：`SnapshotChanged`/`ReceiptResolved` 同步触发；Unity 主线程 marshalling 属于平台层，本任务不提供。
6. **接收侧没有后台队列**：实现有意只允许一条消息在途，以 `MaxMessageBytes` + `ReceiveMessageTimeout` 界定慢读；不会为慢消费者无界缓存。若产品要求“先收后排”的客户端缓冲，需要后续单独设计并设上限。
7. **票据 provider 只是端口**：没有账号/OIDC/JWKS/一次性票据实现，也没有 Android/iOS 安全存储；runner 只保证每次重新调用 provider、不缓存字符串。票据字符串本身在 .NET 中不可清零。
8. **既有 outbox 限制仍在**：本轮未改 `Outbox.cs` / `FileOutboxStore`；明文文件、平台安全存储、断电/目录 fsync、token-bearing 命令拒绝等边界沿用既有 P5.4a 任务报告。
9. **心跳语义只对客户端控制层负责**：真实服务端是否按相同 interval/idle 和绑定字段回应，未在真实 TableService 上验证。
10. **最小测试 WebSocket 服务器不是生产实现**：它只实现测试所需 RFC6455 子集，不覆盖扩展、压缩、复杂分片/控制帧组合。
11. **V4 仍是生产基线；G1 未通过**。本实现是 P5.4a 的增量代码与单元/本机集成证据，不是全链验收。
