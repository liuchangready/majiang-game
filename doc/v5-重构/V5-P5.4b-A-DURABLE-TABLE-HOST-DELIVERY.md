## 2. 持久宿主装配（交付要求 ①）

### 2.1 装配端口

`TableServiceWebHost.Build` 增加 store 模式分支：`TableServiceOptions.StoreMode == TableHostStoreMode.Memory`（P3.4/P5.1 已接受内存模式，原样保留）或 `Postgres`。Postgres 模式下 Build 直接构造：

- `PostgresTableStore`（同一真实 PG 连接，承载 events/receipts/checkpoints/scopes/lease/outbox）；
- `TableHostScopeAuthority`（`ITableHostScopeAuthority`：宿主颁发/撤销玩家 scope 的窄写端口，落同一数据库）；
- `PostgresTableHostRegistry`（`ITableHostRegistry` 的持久实现）。

坏配置/无 DB/key 缺失/迁移检查失败/恢复损坏一律 `TableServiceCapacityException`（准入映射为 SERVER_BUSY 拒绝）或启动失败退出，**从不静默落回内存**。`Program.LoadOptions` 解析 `TABLESERVICE_STORE`（`memory`/`postgres`，未知值拒绝启动）；Postgres 模式强制 `TABLESERVICE_PG_CONNECTION`，并读取 `TABLESERVICE_PG_PAYLOAD_KEY`、`TABLESERVICE_PG_APPLY_MIGRATIONS`、`TABLESERVICE_PG_COMMAND_TIMEOUT_SECONDS`、`TABLESERVICE_PG_MAX_POOL_SIZE`。启动前 `IsStoreSchemaReady` 探针 fail-closed（`TABLESERVICE_PG_APPLY_MIGRATIONS=true` 时先跑 `PostgresTableMigrator`）。

日志只输出脱敏后的异常类型名 + 截断消息（`PostgresTableHostRegistry.Redact`），不打印连接串/key/token/私有 payload（runner 的 `e2e-db-unavailable` 阶段显式断言 stderr 拒绝行不含敏感信息）。

### 2.2 全异步准入门（本轮发现并修复的生产级缺陷）

初版 `PostgresTableHostRegistry` 在 `lock (_createGate)`（monitor）内以 `.GetAwaiter().GetResult()` 同步等待真实 DB I/O（LoadState/恢复/scope 颁发/租约）。该路径跑在 WebSocket 接收链上（`ManagedWebSocket.ReceiveAsyncPrivate → ExecutionContextCallback → AdmitAsync`），被等的 continuation 可能需要被阻塞的线程本身——sync-over-async 死锁。dotnet-stack 栈证据（`thread 0xD698 blocked at ManualResetEventSlim.Wait ← ValueTask[T].get_Result ← RecoverExistingRoomLocked ← CreateHostLocked ← GetOrAdd ← AdmitAsync`，运行史 R2，§6）恰好复现在前台准入路径。

修复为全异步形态（任务书约束 "DB不得在actor锁内做同步GetResult" 的直接落实）：

- `ITableHostRegistry` 增加 default interface method `Task<RoomHost> GetOrAddAsync(string roomId)`，内存注册表继承默认（同步工厂 `Task.FromResult` 包装，已接受 TableService.Tests 的 2 处同步调用不变）；
- `PostgresTableHostRegistry` 用 `SemaphoreSlim(1,1)` 异步门串行创建/恢复；同步 `GetOrAdd` 显式实现为 throw（fail-closed：持久注册表只接受异步准入）；
- `TableSessionHandler.AdmitAsync` 改为 `await _hosts.GetOrAddAsync(...)`；
- 创建/恢复路径全部 await：`LoadStateAsync` → `BootstrapNewRoomAsync`/`RecoverExistingRoomAsync` → `IssueServiceScopeAsync`/`CreateRoomAsync`/`AcquireAsync`/`RecoverFromStoreAsync`/`GetControlSnapshotAsync`；失败路径 `await actor.DisposeAsync()`；
- `DisposeHostsAsync` 的 StopAdmission 扫描持门、disposal 循环在门外 await——关闭路径同样无阻塞 GetResult。

修复后经受限角色（DML-only `mahjong_table_runtime`，与 runner 超级用户路径区分）+ 官方 runner 双重验证（§6 运行史 R2-验证、R3+）。

### 2.3 scope 权威与回执同库

`TableHostScopeAuthority` 是宿主写 scope 的窄端口，内部委托 `IRequestScopeAuthority`（= PostgresTableStore）落 `table_store.request_scope`。准入颁发、撤销、`ReceiptQuery` 全部读/写同一数据库——没有内存影子作授权或回执来源。单桌 actor 的 durable context（commits/timing/lease）也直接挂同一 store。

### 2.4 生产宿主固定端口

runner 揭示的第二个缺口：裸 `Program.Main` 走 `bindPort=0` 临时端口，生产宿主无法在已知地址被访问。补全 `TableServiceOptions.HttpPort`（0=临时端口，单测/裸跑默认）→ `Validate.RequireRange(0,65535)` → `Program` 读 `TABLESERVICE_HTTP_PORT` → `Build(options, keys, IPAddress.Loopback, options.HttpPort)`。runner `Start-TableHost` 设 `TABLESERVICE_HTTP_PORT` 后，host-a 稳定 live 于声明端口（§6 R4→R5 修复证据）。

## 3. 房间生命周期（交付要求 ②）

### 3.1 新房间原子 bootstrap

无 `table_state` 行的房间按序原子落库：服务 scope 行（`IssueScopeAsync`）→ checkpoint-0 行（`CreateRoomAsync`，并发创建者在 INSERT 上以 "Room already exists." 败出 → `ROOM_ALREADY_EXISTS` fail-closed）→ 租约 `AcquireAsync`（败者 `LEASE_UNAVAILABLE`）。赢家租约的 `OwnerEpoch` 交给 commit port 与 actor。

### 3.2 已有房间冷恢复

有状态房间走已接受 `TableActor.RecoverFromStoreAsync`：新 owner epoch、checkpoint + 事件日志经真实 Domain 重放、hash/fingerprint/136 牌/序列连续性校验、`RecoveryStateSink` 安装已验证千术聚合（缺失即 throw，actor 不进 Serving）。恢复返回前宿主对任何会话不可见——无 WELCOME、无可玩基线、不收命令。恢复完成后再取控制快照（`RecoveryGeneration`）与该房持久服务 scope；后续每个信封（subscribe/command/auto-draw）都携带该 generation 过严格恢复栅栏（`TableCommandMapper.Map`/`TableDecisionRuntime.AutoAdvanceDrawAsync` 不再硬编码 `recoveryGeneration: 0L`）。

恢复失败（`!recovery.Recovered`）→ dispose actor → `_failedRooms` 记原因码 → `RECOVERY_FAILED`；readiness 计入 failed rooms（已知不可服务 ≠ 健康空表）。

### 3.3 bootId / UTC / grace / 不续活历史 scope

恢复合同沿用 TableRuntime 既有语义：进程级 `ProcessBootId`（同一进程内重建 registry 不误标跨机重启）；过期/未知 scope 不续活；超时提交不重做（fail-closed 重试证据见 §4/§6）。不重抽牌、不伪造候选——恢复投影即决策来源。

### 3.4 正常关闭

`TableServiceHostRuntime.StopAsync`：Kestrel 停监听 → `DisposeHostsAsync`（StopAdmission 扫描 → 逐 actor `DisposeAsync`，P4.1 已占用的 `TableActor.CloseAsync` 排队语义不动）→ `PostgresTableStore` dispose。旧 owner 关闭后不可再提交（租约语义 + epoch 栅栏，双宿主阶段实证）。已接受 `ITableLease` 端口只有 Acquire/Renew/Get——无释放原语，"dispose lease" 的既有合同语义即停止续约、租约按 TTL 自然过期；成功者必须等过期后经 `AcquireAsync` 合法接管。

### 3.5 checkpoint-0 必须携带全量初始千术聚合（R6 根因修复）

**缺陷**：初版 `RoomHost.CreateInitialCheckpoint` 以 `TableCheatLedgerCheckpoint.FromLedger(ledger)` 写 checkpoint-0 的 cheat 载荷（146 字节，仅账本）。而已接受 actor 构造时（`TableActor` ctor）对自身初始聚合执行 `CheatState.Initialize(economy)` 后**再注册发牌轮**（`TileMarks.RegisterDealtRound(roundId)`，marks.Version +1）：活体初始聚合 Version=1（ledger 0 + marks 1），首次带千术推进的提交（玩家 discard 开 bloom 窗，bloom.Version+1）将绑定提交为 **Version=2 + 含发牌注册的指纹**。schema-1 日志重放只重放 bloom 窗口（`TableRecoveryService` 对 DiscardTile 的 `WithOpenedWindow`），**从不重放发牌注册**——当该提交之后没有更新周期 checkpoint 即停机（快跑形态），恢复只能从 cp-0（仅账本）重建 (Version=1, 无注册指纹) ≠ 绑定 (2, 含注册指纹) → `RECOVERY_STATE_HASH_MISMATCH` fail closed。该缺陷呈**快/慢停机偶发**（复现 7 跑 2 败：失败跑无后续 checkpoint，通过跑有）。

**修复**（仅我方文件，未动 Domain/TableRuntime）：`CreateInitialCheckpoint` 以与 actor 构造完全同构的方式构造初始聚合——`new CheatState(ledger, empty, empty, empty)` → `RegisterDealtRound(round.RoundId)`（幂等，同 id 重复注册返回 Applied）→ `TableCheatLedgerCheckpoint.FromCheatState(...)` 全量编码。`FromCheatState` 载荷保留完整 `_state`，`RestoreCheatState` 直接返回原对象——cp-0、actor 活体、周期 checkpoint 三者同源，恢复从任意 checkpoint 起点重放均与绑定一致。内存注册表走同一 helper 自动受益；已接受 TableRuntime 400 项 harness 自建全量 cp-0，不受影响（其形态与本修复一致）。

### 3.6 owner 实例标识必须每运行时唯一（R6 后暴露的围栏缺口）

**缺陷**：`TableServiceWebHost.Build` 以 `"tablesvc-" + Environment.ProcessId` 作租约 owner 实例标识。已接受租约契约（禁改）的 `AcquireAsync` 允许 **owner_instance 自匹配重获活租约**（重启重claim 语义）：同进程并存的两个宿主运行时（双宿主围栏测试的嵌入形态）共享同一标识 → 第二运行时把异己活租约当作自己的 → 合法接管（epoch+1）→ 对必须拒绝的准入发出 WELCOME。历史运行未暴露它，恰因 §3.5 缺陷让第二宿主以 HASH_MISMATCH 错因拒收；cp-0 修复移除错误拒收后真实缺口显形。

**修复**（仅我方文件）：owner 标识改 `"tablesvc-" + Guid.NewGuid().ToString("N")`，每 `Build` 唯一；保留 runner 断言的 `tablesvc-` 前缀。异己活租约回到 `Held` 快速拒收路径；崩溃宿主的房间由后继进程**等 TTL 过期后合法接管**（runner `TABLESERVICE_LEASE_TTL_SECONDS=5`，phase-2 冷恢复等待 ≤5s，180s 超时余量充足）。配套将新增套件中两处对旧碰撞行为的隐性依赖对齐真实租约语义：`SameBootRecovery` 补上其注释早已声明却缺失的第一宿主优雅停止；`RevokedScope` 在重启第二运行时前等待 abandoned lease 过期（与 `ColdRecovery` 既有 6s 模式一致）——不放松任何断言，是对"租约无释放原语"这一已接受合同的显式建模。

### 3.7 跨进程票据 jti 碰撞与 runner 退出码失明（R7 双根因修复）

**缺陷一（测试 worker）**：`WorkerTicketSigner.SignTicket` 以进程级静态计数器生成 `jti-N`——每个 worker 都是独立进程，计数器逐进程归零：runner 的每个阶段都铸造 `jti-1`。而已接受消费登记表（禁改）按 `jti` 一键去重、已消费记录保留至票据有效期（240s+skew）——多阶段共用同一存活宿主时，后续阶段的诚实新准入被误判为 `DuplicateJti` 重放 → 4401。R7 实证：host-b 仅 3 连接 = phase-2 准入成功（消费 jti-1）+ revoked-scope worker 被拒 + crossaccount B 账号被拒，后两者同为 jti-1 碰撞。已接受进程内套件从未暴露：单 signer 进程内计数器自增、每测试宿主注册表全新。修复：jti 改 `"jti-" + Guid.NewGuid().ToString("N")`（每签名全局唯一，仿真实签发方），assignment 派生不变。

**缺陷二（runner）**：本机 PS 5.1 实测（变体 A–E 对照）：`Start-Process` 一旦重定向 stdout/stderr，返回 Process 对象的 `.ExitCode` 在进程退出后读数为**空**，`if (-not $exitCode) { $exitCode = 0 }` 把空强制为 0——`Invoke-Native` 的退出码门在本机**从未生效**，子进程失败只能靠后续断言（缺 JSON/计数不符）暴露。R7 后果：`e2e-revoked-scope-receipt` 在 worker 实际以 4401 失败的情况下打出**空洞 PASS**（该阶段此前只调 worker、零断言）；`e2e-db-unavailable` 的 `exit==0 → throw` 反向门（fail-closed 不成立时本应 FAIL）形同虚设。修复（全部 runner 内）：① `Invoke-Native` 改用原生 `System.Diagnostics.Process` + 异步泵（实测对照：cmd exit 3 → 3，dotnet 宿主失败 → 非零，成功路径 → 0；泵的最终形态含增量排空，见 §3.8）；② revoked-scope 阶段补齐对 `phase2-revoked-scope.json` 的证据断言（receiptFound / sameKeyRetryFailedClosed / historicalScopeStillAuthorized / ledgerRows==1 / expectRevokedScope）；③ `e2e-db-unavailable` 改经 `Invoke-Native` 拿真实退出码；④ `Start-TableHost`/`Start-WorkerHold` 失败消息不再引用失真的 ExitCode（存活探活仍靠 `HasExited` 轮询，不受影响）；⑤ `Stop-TableHost` 强杀记录仅在真实读到退出码时才落 `exitCode` 字段，不伪造 0。长驻进程启动（宿主/hold worker）保留 `Start-Process`：其轮询依赖重定向文件的**实时可见性**，泵式完成时落盘会破坏 hold-open 形态；这两处无以退出码为条件的门。

### 3.8 管道 EOF 属于最后句柄持有者（R8/R9 挂起根因，本轮第二处 runner 修复）

**现象**：`Invoke-Native` 重写为原生 Process 后，runner 连续两轮（R8/R9）在 **cluster 阶段挂死**：runner 进程存活、零子进程，`pg-start.log.stdout`/`.stderr` 已生成但合并的 `pg-start.log` 永不出现，`createdb`/`psql` 产物缺失——流程停在 `pg_ctl start` 内部。第一轮（R8）误判为轮次边界杀死后台任务；R9 同签名复现后才定位真实根因。

**根因**：管道 EOF 属于**最后一个句柄持有者**，不属于直接子进程。`pg_ctl -w start` 完成自身职责后退出，但它拉起的 postgres 整场存活并**继承**了 pg_ctl 的 stdout/stderr 管道写端——`ReadToEndAsync` 等的 EOF 永远不会到达，`GetAwaiter().GetResult()` 无限阻塞。`dotnet build` 背后驻留的 Roslyn 编译服务器（VBCSCompiler）同理。旧实现（`Start-Process` 重定向到**文件**）没有 EOF 语义，所以此雷从未被踩到——它是重写新引入的。

**修复**：管道排空改为**增量式**——子进程存活期内持续 `ReadAsync` 循环（既防 pipe-full 死锁阻塞子进程写日志，也不再等待任何 EOF）；子进程退出后给在途字节一个 10s 有界宽限；全程受全局 deadline 约束（超时强杀并抛出）。累积**实际到达**的字节，而不是等待一个孙进程可能永不发送的 EOF。三形态机制验证（普通退出/非零退出/孙进程句柄滞留）全过后才投入正式运行；R10 起 cluster/xml-selfcheck/fresh-build 首次在该实现下 PASS。

### 6.5 round 3（新信息追加）：冷恢复租约安装窗口与有界重试

**追加依据（新信息，非任务书已知缺陷）**：R16 行所指外部并行运行的 `e2e-phase2-cold-recovery` 以 `RECOVERY_STATE_CHANGED` 拒绝收场——同一运行内回归四连套件全绿，同树代码、官方 runner 形态。符合"仅当出现新信息时才允许追加"条款，登记为 round 3。

**根因链（实测闭环）**：

1. **结构性窗口**：冻结的租约安装路径（禁改 `TableActor`/`TableRecoveryService`）先 claim 租约（`AcquireAsync` 位于 `RecoverAsync` 最前），随后在 actor 串行队列上重建全房（checkpoint + 事件日志真实 Domain 重放 + hash/指纹/136 牌/序列校验 + `RecoveryStateSink` 安装），最后在**两道围栏**复验后才安装：fence-1 终验（拒绝码 `RECOVERY_STATE_CHANGED`）与 fence-2 `RevalidateRecoveryInstallAsync`（`STALE_OWNER_EPOCH`）。重建期间**没有任何续约机会**——恢复窗口 = 全房重放时长，而 TTL 是配置值（下限 `LeaseTtlSeconds must be 5..3600`，runner/套件均用 5s）。
2. **窗口实测**（round-3 计时埋点，37 个样本）：min 165ms / p50 1337ms / max **7431ms**；暖基线 242ms（`wss-ttl5-233236`）。最坏样本 `p54b-anchor-ckpt-hand` 7431ms > 5000ms TTL → 终验时自家租约已过期被 fence 正确拒绝。负载越重窗口越长——这正是该失败只在套件/全链负载下偶现、单测直跑从未复现的原因（R16 外部运行即套件满载 822.8s 场景）。
3. **同一房间的自然实验**（五跑，同测试同房）：窗口 4166 / 2116 / 1974ms 首试即过；**7431ms 被 fence-1 拒**；重试 attempt=2 以 1407ms 完成 `recovered=True`。窗口是否越过 TTL 唯一决定首试成败，且 fence 拒的是自家 claim——缺陷在窗口不在校验。

**修复（仅我方文件 `PostgresTableHostRegistry.cs`，未动 Domain/TableRuntime/Infrastructure）**：

- `RecoverExistingRoomAsync` 有界重试：仅对两 fence 码（`RECOVERY_STATE_CHANGED`/`STALE_OWNER_EPOCH`——同为"围栏验证的世界在安装前移动了"的乐观并发瞬态）触发；dispose 被拒 actor → `WaitForAbandonedLeaseExpiryAsync`（轮询 `ITableStore.GetAsync`：租约缺失/已过期/**同 owner 即返**——`PostgresTableStore` upsert 的 `OR owner_instance = EXCLUDED.owner_instance` 子句使自家废弃租约即时重取；仅异己活 owner 值得有界等待，deadline = now + TTL + 2s）→ **第二次完整恢复尝试**（重跑全部完整性校验与两道围栏，不跳过任何检查）→ 第二次拒绝仍终态 fail-closed（dispose → `_failedRooms` → `RECOVERY_FAILED`）。恰一次重试，无无限循环。

### 10.1 D-R2-01（MAJOR）合法鸣牌后的首弃锚点

- **根因**：tier-2 恢复锚点把“当前牌河第一项”当作历史开局首弃。吃/碰/明杠会把被鸣走的弃牌物理移入副露，合法 checkpoint 的当前河为空或第一项已是较晚弃牌，于是合法存档被 `RECOVERY_ANCHOR_UNAVAILABLE` 拒绝。
- **修复**（`PostgresTableHostRegistry.BuildRecoveryProjectionSource`）：
  1. 首选 **checkpoint committed history** 中该首弃的 `TableEventRecord`（seat + 物理 tile 唯一），用其**全局 EventSeq** 绑定 `CommittedFactsPayload.EventFacts`；校验 fact 的 type/tile/EventOrdinal/CommandVersion 与 history 逐项一致，且 CommandVersion ≤ checkpoint state version。

  3. 无裁定锚点**绝不猜值**：构造可继续（结构合法），但投影第一次真正发布该 tsumogiri 时 fail closed。真实 actor 的 checkpoint 总有 history/EventFacts；该分支只服务缺少证据的合成载荷。
