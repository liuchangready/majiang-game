### [B1-BLOCKER-02] 同一 assignment 的 Lobby 新票被 TableService 消费登记表拒绝

**严重级别：BLOCKER（阻断要求 4 的同 assignment 杀进程/新 PID 恢复；等待旧票过期不是安全恢复）**
**位置：** `dotnet/src/Mahjong.TableService/TableTicketConsumptionRegistry.cs:277-295`：只要 `_assignments` 中已有该 assignment 记录，任何不同 jti 都返回 `DuplicateJti`，记录保留到旧票 `expiresAt + clockSkew`；`Consume` 的注释明确“one assignment ⇒ one jti for whole validity”。
**复现：** 同一 B1 suite 在首张票 admission 后，对同一 account/assignment 立即由 Lobby `POST /v1/table-tickets` 重签，再用新票 WSS 准入；`suite-summary.json` `immediateReissueRejected=true`、`immediateReissueDetail=WS_CLOSE_4401`。服务端日志 `ticket consumption refused` → `close sending INVALID_TOKEN`。
**实际 vs 期望：** 实际 4401，无法在 TableService 不重启的情况下用同一 assignment 的新票重连；期望 Lobby 的短 TTL/重连语义与 TableService 的一次性消费语义对齐（同 account/role/room/seat 的新 jti 在旧连接已释放或顶号时安全接管），或明确要求等待旧票过期并证明 assignment 仍有效。
**证据：** `suite-summary.json`（同上）；`table.stdout.log`（同上）；复现命令同上。
**修复要求：** 由 TableService/安全 owner 决定并实现的 assignment 级消费/接管模型；不得在 worker 中伪造 jti 或直接写 `request_scope`/`table_ticket`。
**验收断言：** 旧票 TTL 内重签的新票能被拒绝且旧票不被重放；安全接管路径下新票 WELCOME，旧连接 4403 终止，`request_receipt`/`table_event` 无第二次副作用；或产品明确 `scope/assignment` 到期后的 BLOCKED/unknown 语义。

### [B1-BLOCKER-03] 首回执与回执查询的 canonical digest 不同域，Rejected 查询 digest 缺失

**位置：**
- 首回执：`TableService/TableSessionHandler.cs:1538` 用 `TableCommandMapper.MapReceipt(result, digestHex)`，`digestHex` 来自 `TablePayloadSha256`（业务 payload 裸 SHA-256）。
- Client：`Client/TableSession.cs:1373-1379` 把首回执 `CanonicalPayloadSha256` 与 `OutboxEntry.DigestSha256`（`PayloadDigest`，domain-prefixed）比较；不一致即 `RequestIdConflict`。
- 回执查询：`TableSessionHandler.cs:1837-1851` `MapLookupReceipt` 用 `receipt.CanonicalPayloadDigest.ToHex()`（domain-prefixed），与首回执裸 SHA 不同；Rejected receipt 的 DB `canonical_payload_digest` 为本轮观测为空。
**复现：** round-2 final14 suite 的 same-key 探针：首 receipt `Rejected/ROUND_MISMATCH`，裸 SHA 与 payload 匹配；lookup 的 `CanonicalPayloadSha256` 为空/不同域，`ReceiptDigestDomainMismatch=true`；`NegativeFacts[0].ExpectedCanonicalDigestHex=""`。同时 `suite.json` 的 `ServerReceiptStatus=Applied` 但 Client pending=1。
**实际 vs 期望：** 期望同一 request 的首回执、lookup、Client outbox 使用同一 canonical digest 定义；实际首回执裸 SHA、lookup domain digest、Rejected lookup 无 digest，Client 会将合法首回执判为冲突。B1-BLOCKER-01 的缺 scope 掩盖了该缺陷，修 scope 后仍会阻断。
**证据：** `suite-summary.json` `ReceiptDigestDomainMismatch=true`；`negative-facts-audit.json`（`same_key_different_payload_and_kind` expectedDigest 空）；`table.stdout.log`；报告 hash 清单。
**修复要求：** 生产 owner 统一 digest 契约（建议服务端首回执和 lookup 都回填 `CanonicalPayloadDigest`/`PayloadDigest` 的同一个 domain-prefixed 值；Rejected 也保存/返回同一 digest），或在 Client 明确按协议转换但不得放宽身份校验；测试侧不得把不匹配的 digest 当 PASS。
**验收断言：** 首回执、lookup、outbox 的 canonical digest 三者相等（敏感值以 hash 引用）；Rejected 回执也具备稳定 digest；Client 收到 APPLIED 后不产生 `RequestIdConflict`。
