### [B1-BLOCKER-01] 生产 receipt 缺 RequestScope，生产 Client 丢弃该 receipt

**严重级别：BLOCKER**
**位置：**
- `dotnet/src/Mahjong.TableService/TableSessionHandler.cs:2491-2496` `BuildReceipt` 只调用 `BuildEnvelope(MessageType.Receipt, receipt, …)`，未写 `Envelope.Scope`；`BuildEnvelope` 在 `:2380-2391` 也不设置 Scope。
- `dotnet/src/Mahjong.Client/TableSession.cs:1353-1361` `HandleReceiptAsync` 在 `envelope.Scope == null` 时直接 `return`，从不调用 `FindTracked`/`ResolveTrackedAsync`。

**复现：**
```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File tools/ci/verify-v5-https-admission.ps1 `
  -DotnetPath D:/Unity/dotnet/dotnet.exe -PgPort 58471 -LobbyPort 58572 -TablePort 58573 `
  -Root <...>\artifacts\b1-final9-pg -LogDir <...>\artifacts\b1-final9-logs
```
**实际：** wrapper exit 2；`suite-summary.json`：`blockerCode=CLIENT_RECEIPT_SCOPE_MISSING`，`serverReceiptObserved=true`，`serverReceiptStatus=Applied`，`serverReceiptCommandVersion=1`，`serverReceiptScopePresent=false`，`clientPendingAfterServerReceipt=1`。Client 入站 trace 含 `Receipt`，但 TableSession 未 resolve；`TableSession.LastError=PROTOCOL_VIOLATION`（收到空 code 的 Close 的次生症状，见 B1-MAJOR-01）。同一 receipt 由 raw WSS 以原 scope/requestId 查询为 `Found/Applied/1`（`rawReceiptQueryFound=true`），证明服务端已提交、签发正确，缺陷在信封/客户端消费契约。
**期望：** 真实 Client 收到 APPLIED receipt 后 outbox 清零，`PendingCommands.Count == 0`；之后才能进入 exact-byte replay 与未知结果链。
**证据：** `suite.json` SHA256 `F19564C7042B06BB24E7EFC1B4B57692CC39E85F8F12C3BB78A3CB6BD6B3946E`；`suite-summary.json` `C060763CA1F40C4D7606A821B74742F99E6B074C9359462F29143A24D834E05B`；`suite.log` `3B3CEE80A68AC834975118DCC8E8D3B336BE9E332751740CB6F2074CE67873CE`；`table.stdout.log` `D621B10716098B221CECF20BFAAAD66D00DEE96CF50280CD8AFE43BC43D0AE0D`；完整 manifest `94FA7358880D4C1D4B2006D0A5DFA69D670A024CB99D80EB122470D77498AF62`。
**修复要求（二选一，生产 owner 决定）：**
1. 服务端在 `BuildReceipt`/`BuildEnvelope` 回填当前 `RequestScope`（scopeId/accountId/role/roomId）；或
2. 客户端 `HandleReceiptAsync` 先按 `envelope.RequestId` + 当前 tracked entry 查找，`Scope == null` 时使用该 entry 的 owner scope 做账户校验（不能无条件信任）。
不得在测试 worker 的 `ReceiptLossChannel`/测试客户端注入伪 scope 冒充通过；不得放宽 `TableSession` 对账户/角色/room 的校验。
**验收断言：** 同一 B1 runner 下 `clientPendingAfterServerReceipt=0`；正常动作 receipt 的 `CommandVersion` 与 PG `state_version` 一致；随后 exact-byte replay 返回同一 receipt identity；再进入 A11/A12。

### [B1-BLOCKER-02] 同一 assignment 的 Lobby 新票被 TableService 消费登记表拒绝

**严重级别：BLOCKER（阻断要求 4 的同 assignment 杀进程/新 PID 恢复；等待旧票过期不是安全恢复）**
**位置：** `dotnet/src/Mahjong.TableService/TableTicketConsumptionRegistry.cs:277-295`：只要 `_assignments` 中已有该 assignment 记录，任何不同 jti 都返回 `DuplicateJti`，记录保留到旧票 `expiresAt + clockSkew`；`Consume` 的注释明确“one assignment ⇒ one jti for whole validity”。
**复现：** 同一 B1 suite 在首张票 admission 后，对同一 account/assignment 立即由 Lobby `POST /v1/table-tickets` 重签，再用新票 WSS 准入；`suite-summary.json` `immediateReissueRejected=true`、`immediateReissueDetail=WS_CLOSE_4401`。服务端日志 `ticket consumption refused` → `close sending INVALID_TOKEN`。
**实际 vs 期望：** 实际 4401，无法在 TableService 不重启的情况下用同一 assignment 的新票重连；期望 Lobby 的短 TTL/重连语义与 TableService 的一次性消费语义对齐（同 account/role/room/seat 的新 jti 在旧连接已释放或顶号时安全接管），或明确要求等待旧票过期并证明 assignment 仍有效。
**证据：** `suite-summary.json`（同上）；`table.stdout.log`（同上）；复现命令同上。
**修复要求：** 由 TableService/安全 owner 决定并实现的 assignment 级消费/接管模型；不得在 worker 中伪造 jti 或直接写 `request_scope`/`table_ticket`。
**验收断言：** 旧票 TTL 内重签的新票能被拒绝且旧票不被重放；安全接管路径下新票 WELCOME，旧连接 4403 终止，`request_receipt`/`table_event` 无第二次副作用；或产品明确 `scope/assignment` 到期后的 BLOCKED/unknown 语义。

### [B1-MAJOR-01] Client 收到空 code Close 后 `PROTOCOL_VIOLATION`

**严重级别：MAJOR（次生症状/独立需定位）**
**位置：** `dotnet/src/Mahjong.Client/TableSession.cs:1977-1996`：`Close.Code` 为空时置 `PROTOCOL_VIOLATION` 并进入 Faulted。

**期望：** 任何服务端 Close 都带稳定 code；Client 在已收到 APPLIED receipt 后不应因无 code Close 丢失已确认结果（与 B1-BLOCKER-01 一并修复）。
**证据：** final9 `suite-summary.json`，final2 `table.stdout.log` 第 31 行 `close reserved SLOW_CONSUMER`（历史运行保留，未重写）。
**修复要求：** 定位空 code Close 的产生路径（`TableSessionHandler.SendCloseAndCloseAsync`/`Directive`）；客户端 close code 不得默认为空；对真实 5 客户端 + 250ms tick 做持续回归，不把 50ms 当已支持能力。
