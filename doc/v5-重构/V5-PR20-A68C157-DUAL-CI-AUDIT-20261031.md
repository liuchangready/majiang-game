2. 第一次取消通常表现为 `TaskCanceledException`（`OperationCanceledException` 的子类）；
3. 一旦 socket 已 `Aborted`，下一次 `ReceiveAsync` 就抛出与 CI 完全相同的 `WebSocketException`。

### 5.3 为什么本次抛出的是第二种异常

CI 记录的异常不是 `TaskCanceledException`，而是 **已经 Aborted 的 socket 上的下一次 `ReceiveAsync`**（invalid state）。这要求：

1. spectator 的 baseline 20 s 读取已成功（否则会在 line 90 失败，而不是 line 110）；
2. 500 ms 采样的某一次读取在 token 取消的同一窗口内**返回了一帧**，测试把该帧加入 `spectatorFrames` 并进入下一轮；
3. 该次取消已把 socket 置为 `Aborted`；
4. 下一轮 `ReadUntilAsync` 再次 `ReceiveAsync`，抛出 XML 中的 `WebSocketException`。

这是由调用栈 + helper 代码 + 探针可推出的**唯一与现有代码一致的链路**；测试的 `finally`（line 130-138）不会在 line 110 的异常之前执行 `DisposeAsync`，服务端也没有在失败前对该连接 `send fault`/主动 abort。服务端 `room-nopriv` 日志显示 5 个连接被 admitted，之后因客户端断开出现 `receive exit ... ConnectionClosedPrematurely` / `teardown enter state=Aborted`，这些都在客户端异常之后，属于清理，不是原因。
