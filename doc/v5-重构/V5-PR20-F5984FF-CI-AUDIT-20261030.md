## 6. 根因分析：已证事实、机制与缺口

### 6.1 已由原始 artifact 证明

1. 失败 run 是 `pull_request`，实际 checkout `aafd1c32`；push run 是 `push`，checkout `f5984ff`。两者的 tree 全等，目标测试 blob 全等；**源码树差异可以明确排除**。
2. 唯一失败是 LocalHost 的 `ClientPassOnRonSetsFuritenAndColdRestartKeepsItUntilTheNextDraw`，断言 `:1063`；LocalHost **115/1/0**，全 job **2,641/1/0**，native exit 1。
3. 同一失败在 e22 的 `40932995962` 已经出现；两份 direct log 除 elapsed time 外完全相同。**这不是 f5984ff 新引入的代码差异**。
4. 测试在 `:1010` 已经断言 `afterPass.PrivateView.Furiten == true`，在 `:1014` 已经断言 `runtime.ActorForTest.FuritenForHost.IsTemporary(0) == true`；失败发生在更后面的 `:1063`。因此失败时**内存/投影中的 furiten 曾经为 true**，不是 pass 从未设置 furiten。
5. `LocalTableStore.CommitAsync` 在返回 receipt 前调用 `_inner.CommitAsync`、构造 candidate、`Persist(candidate)`，`CompleteWrite` 在 `LocalWriteVerdict.Committed` 时安装 `_save = candidate`（`LocalTableStore.cs:897-986`、`:1818-1832`）。**pass 的 true 是同步持久化后才返回 receipt 的**；`:1063` 的 false 不能由“pass 还没写盘”解释。
6. 清除 temporary furiten 的代码路径只有摸牌：`TableActor.cs:4598-4618` 在 `TileDrawn`/`RinshanDrawn` 或 `DrawTile` 时执行 `WithTemporary(seat, false)`。`LocalTableHostOptions.AutoPlay` 默认 `true`（`LocalTableHost.cs:61`）；`LocalTableRuntime` 构造时启动 driver（`LocalTableRuntime.cs:88-92`）；`LocalTableDriver.DriveAsync` 约每 15 ms tick（`LocalTableDriver.cs:96-143`）。`P41Harness` 没有设置 `AutoPlay=false`。
7. 测试从 `:1010` 的 true 到 `:1063` 的 store 读取之间，没有停止 server-side driver（只停止客户端 pump），也没有等待/校验 pass 的 state version；这给“driver 推进到 seat 0 摸牌并清除 furiten”留下窗口。

### 6.2 机制（与既有受控实验一致）

```text
[测试] 提交 pass
  -> [actor/store] 原子提交 pass：seat 0 temporary furiten = true；save 同步写入 true
  -> [测试] 投影/actor 断言 true（:1010/:1014）
  -> [测试] 提交 forged Ron，等待 rejected receipt
  -> [driver] 继续 tick，seat 1..3 摸打，推进到 seat 0 摸牌
  -> [actor/store] DrawTile 清除 temporary furiten；save 写入 false
  -> [测试] 重新打开 LocalTableStore，读取 LoadTemporaryFuriten()[0] = false（:1063）
```

既有 e22 诊断的受控实验（本审计未重跑，作为先前证据引用）在独立归档副本中：

- 在 rejected Ron 后注入 750 ms：`DIAG-AFTER-PASS state=7 furiten=False`，同一 `:1063` 失败；
- 在同一位置 `StopAsync()` driver：`state=5 furiten=True`，同一断言通过；
- 两组探针只差 driver 是否继续推进。

因此“测试观测竞态”机制是**有代码路径 + 受控实验支持**的，而不是凭“同树一绿一红”猜测。测试只改一个文件、在 pass 前停 driver 的 patch 也确实存在（`V5-LOCALHOST-FURITEN-RACE-REMEDY-TEST-FIX-20261030.patch`），但它在 f5984ff **没有落地**：目标测试 blob 仍是 `d5486ea...`，`git diff 54c460a f5984ff -- dotnet tools .github` 为空。

### 6.3 仍未证明 / 缺失证据

- **CI 当次精确交错未观测。** artifact 没有失败瞬间的 `.save`、`stateVersion`、`TemporaryFuriten` 数组、driver tick 时间或线程调度 trace；无法证明“这一次”确实是 seat 0 摸牌在 `:1063` 前发生，而不是另一个时序。故精确根因 = **BLOCKED/UNKNOWN**。
- **生产 durability 缺陷未证明。** pass 的 true 是同步持久化后才返回；后续 draw 清 true 是规则行为。没有证据表明“receipt 已 Applied 但 true 从未落盘”。不能把测试观测失败写成产品 furiten 逻辑错误。
- **测试补丁未在 CI 验证。** 没有重跑，也没有把 patch 应用到 f5984ff；不能写“已修复”或“flaky 已消除”。
- **不是已证明的“随机 flaky”。** 同代码多 run 出现不同结果，说明对时序/环境敏感；但没有 retry 证据、没有失败瞬间状态、没有平台资源 trace。不能据此说“重跑必过”或“与代码无关”。更准确的表述是**同一测试代码的时序相关观测竞态**。
- **平台差异只是观测，不是已证原因。** 两 run 的 OS/image/runner version 相同；region 分别为 `southcentralus`（PR）与 `westus2`（push），runner ID 不同。PR 与 push 的 LocalHost suite 时间为 13.937 s / 14.005 s，未显示全局变慢；region/调度只能列为未排除的间接因素。
- **构建非确定性不构成因果证据。** 同 tree 的 `Mahjong.Infrastructure.Tests.dll` 两 run 分别为 `2EA58EC4...` 与 `9E98C2E0...`；XML/meta 也因时间戳/路径/ID 不同而哈希不同。这证明“逐字节可重复构建”不成立，但没有证据表明构建差异改变了测试语义。
- **测试顺序/并行不是解释。** 该用例在两次 run 中均为排序第 99 个，前后用例相同；LocalHost 全量时间接近。
- **PR merge 内容已排除。** merge tree 与 head tree 全等，且 merge commit signature verified；不是“base 合入导致另一份代码”。
