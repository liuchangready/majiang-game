# V5 复核与返修协议（Review–Rework Protocol）

日期：2026-10-24  
状态：执行规则，适用于 V5 全部需要独立复核的任务（P0.1 证据类、P3.x 运行时类、P4/P5 集成类）。  
目的：把“逐轮挤牙膏式复核”改为“一次性完整缺陷清单 + 批量返修”，减少无谓轮次、暂停等待和上下文重建成本。

---

## 1. 复核方：每轮一次给全

1. **一次复核 = 一份完整缺陷清单。** 禁止只报 1 条、等返修后再报下一条，也不得把已经复现的缺陷留到下一轮。
2. 清单必须覆盖下列全部维度，逐项确认“无问题”或“有缺陷”：
   - 范围与路径：expectedFiles、越界文件、工作树/分支、未提交改动；
   - 假绿与误 PASS：skip、空测试、旧产物、编译失败被掩盖、`Total=0`、刷新摘要绕过结构校验；
   - 功能正确性：领域规则、边界、终态不可复活、136 张守恒、算分/役种；
   - 并发、时序与恢复：deadline、租约、控制代次、冷恢复、幂等、重放；
   - 安全与隐私：私有牌/账本/种子、公开流白名单、票据、日志脱敏；
   - 证据与口径：命令、exit、真实计数、日志/SHA、PASS/FAIL/BLOCKED/NOT_RUN 不混用；
   - 环境与平台：PG/WSS/Unity/IL2CPP/设备缺口如实标注；
   - 文档一致性：结论与代码、实测、历史记录一致，不夸大。
3. **每条缺陷必须可直接执行**，字段固定：

   ```text
   [ID] D-<轮次>-<序号>
   严重级别：BLOCKER | MAJOR | MINOR
   位置：<文件:行/函数>（或文档章节）
   复现：<原样命令/脚本/输入；只读实仓、只写独占 TEMP>
   实际：<原始输出/计数/exit>
   期望：<应有行为/断言>
   证据：<日志路径、SHA-256>
   修复要求：<具体改法/禁止事项>
   验收断言：<返修后必须实际跑的命令与期望结果>
   ```

4. **同类缺陷合并**为一组，给出统一修复要求和统一负例矩阵，不拆分凑数。
5. **允许追加的唯一理由是新信息**：返修引入了新代码、环境变化、或发现了此前不存在的攻击面。追加时须在清单开头说明“为何上一轮不可发现”。
6. 复核方在发出请求前，必须按 §4 检查清单自检；无法一次给全时，明确写出阻塞原因和已确认部分，不得用“再检查一遍”代替清单。

---

## 2. 返修请求（rework prompt）必须包含

每一条 rework prompt 必须原样包含以下段落（可放在开头）：

```text
【复核完整性要求】
本轮必须一次性给出全部已知缺陷，不得只报一条或把已知可复现问题留到下一轮。
每条缺陷须含：ID、严重级别、位置、复现命令/脚本、实际 vs 期望、证据路径、修复要求、验收断言。
同类缺陷合并，给出统一修复要求与统一负例矩阵。
返修方须在同一轮内批量修复全部 BLOCKER/MAJOR，并逐条给出修复映射与验证证据；
不得用 skip、空测试、放宽断言、刷新摘要或旧产物获得绿色。
仅当出现新信息时才允许追加缺陷，并须说明此前为何不可发现。
```

并明确：
- 本轮缺陷总数与严重级别分布；
- 哪些是上一轮遗留、哪些是本轮新增；
- 返修交付物：逐条修复映射、负例、定向与全量命令/计数/exit、日志路径、commit、clean status；
- 禁止事项：只修第一条、把已知缺陷留到下一轮、修改统一 verifier 放行、删除或弱化既有探针。

---

## 3. 轮次收敛与升级

| 条件 | 动作 |
|---|---|
| 连续 2 轮无新增缺陷 | 进入验收，不再发起返修 |
| 同一类缺陷第 3 次出现 | 升级人工裁决，停止自动返修 |
| 单轮新增 BLOCKER > 5 条 | 暂停任务，重排范围/设计，不继续打补丁 |
| 复核方无法一次给全 | 明确标记 `REVIEW_INCOMPLETE`，说明原因；该轮不计入“无新增缺陷” |

返修方每轮结束须报告：本轮修复的缺陷 ID、未修复项及原因、新增风险。不得把“本轮通过”写成“任务完成”，阶段结论仍按 G0–G5 判定。

---

## 4. 复核检查清单

发出返修请求前逐项打勾：

- [ ] 范围：expectedFiles 与实际 diff 一致；无越界文件；工作树干净或已说明；
- [ ] 假绿：无 skip/空测试/旧 DLL/`Total=0`；编译失败不会被旧产物掩盖；
- [ ] 功能：关键规则、边界、终态、守恒均有真实断言；
- [ ] 并发/恢复：deadline、租约、代次、冷恢复、幂等、重放均有用例；
- [ ] 安全/隐私：公开流无暗牌/种子/私有账本；错误路径不泄露；
- [ ] 证据：命令可复制、exit/计数/SHA/日志路径可复核；
- [ ] 口径：full/partial、PASS/FAIL/BLOCKED/NOT_RUN 与事实一致；
- [ ] 环境：PG/WSS/Unity/IL2CPP/设备缺口已单列，未冒充通过；
- [ ] 文档：结论、分母、历史失败记录一致，未改写历史。

---

## 5. 反模式（禁止）

1. 每轮只报一个缺陷，用多轮“挤牙膏”代替一次完整复核。
2. 用“再检查一下”作为返修理由，却不给出具体缺陷与断言。
3. 把已知缺陷留到下一轮，以延长任务或规避本轮验收。
4. 通过删除/弱化既有探针、放宽 verifier、增加 skip 来获得绿色。
5. 把“组件通过”写成“G1/G3/G5 通过”，或把本地结果写成远端 CI 通过。
6. 在返修中扩大 scope、顺手修改无关文件或覆盖其他任务的改动。

## 6. 对当前三个在途任务的适用方式

对 `thread_20261024_081554_9483`（P3.4）、`thread_20261024_055105_a2cb`（黄金目录）、`thread_20261024_065145_3e3c`（追踪矩阵）：

- 下一轮复核请求直接使用 §2 模板，并在清单中合并此前各轮已确认的遗留缺陷；
- 已确认但未修复的项标为“遗留”，不得当作新发现重复计数；
- 返修方在同一轮内批量修复全部 BLOCKER/MAJOR 后再送审；
- 若复核方仍只能给出单条缺陷，按 §3 记 `REVIEW_INCOMPLETE`，不进入下一轮返修。

本协议不改变 G0–G5 门槛，也不把“轮次减少”当作验收通过；V4 仍是唯一生产基线。
